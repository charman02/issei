# Architecture

Issei is a full-stack app for sending one recipe from the person who cooks it to
the person who just tasted it and asked for it (*issei* = "first generation").
A recipe here is attributed to a person, its imprecise measures are preserved
verbatim rather than normalized, and the knowledge an ingredient list can't hold
lives as a note on the individual step. The recipient reads the whole thing from
a capability link with no account. The UI is a warm, playful "kitchen" (bold
sticker / color-block design). This file is a practical map of how that codebase
is organized and what each piece does. For the positioning and the explicit list
of things the app does *not* do, see `POSITIONING.md`.

> **Note on the "garden" era.** An earlier UI rendered each recipe as a plant
> that grew seed→sprout→sapling→tree, and the Kitchen as a garden of those
> plants. That UI was replaced by the current kitchen design. The backend still
> *computes* growth fields (`growth_stage`/`growth_vitality` via
> `services/growth.py`) and returns them on `RecipeResponse`, but the frontend
> no longer surfaces them. The garden UI and its docs were removed once the
> kitchen design was locked in; they remain in the project's git history for
> anyone who needs to see how it worked.

> **Note on the removed lineage model.** Recipes used to form generational trees
> (`parent_recipe_id`, a `ghost_ancestors` table, `lineage_relation`, root-bound
> visibility, `GET /recipes/{id}/lineage`, `services/lineage.py`). That was
> removed in commit `8a3b734`: the app is a bridge between two people, not a
> family network. **There are no ancestors, descendants, roots, branches or
> subtrees anywhere in the current code.** `services/lineage.py` is now
> `services/sharing.py`; on the frontend `api/lineage.js` is now `api/sharing.js`
> and `lib/lineagePayload.js` is now `lib/originPayload.js`. The one thing kept
> is `Recipe.origin_attribution` — the "from Lola" byline, which is a fact about
> one recipe rather than an edge between two.

For *why* the backend is built the way it is (tech choices, design trade-offs),
see `README.md`. For planned features, see `FUTURE.md`. This file is the
"where does X live and what does it do" reference.

The project has two halves:

- **Backend** (`app/`) — a FastAPI REST API. Stores data, enforces auth, does
  the recipe math. Talks to PostgreSQL (prod) / SQLite (local).
- **Frontend** (`frontend/`) — a React single-page app. The UI users actually
  touch. Talks to the backend over HTTP.

They are completely separate programs. The frontend runs in the browser; the
backend runs on a server. They communicate only through HTTP requests (JSON).

## Backend (`app/`)

FastAPI app. The request flow is layered: a request hits a **router**, which
validates input against a **schema**, calls into a **service** (for business
logic) or directly queries a **model**, and returns a **schema** as JSON.

```
HTTP request
   ↓
router  (app/routers/)      endpoint definitions, auth checks
   ↓
schema  (app/schemas/)      validate request, shape response (Pydantic)
   ↓
service (app/services/)     business logic — scaling, conversions
   ↓
model   (app/models/)       database tables (SQLAlchemy ORM)
   ↓
database (Postgres / SQLite)
```

| File / folder | What it does |
|---|---|
| `main.py` | App entry point. Creates the FastAPI app, configures CORS, and mounts all the routers. This is what `uvicorn` runs. |
| `config.py` | Reads settings from the `.env` file (database URL, JWT secret, token lifetime, Cloudinary keys) into a typed `settings` object. |
| `database.py` | Sets up the SQLAlchemy engine + session. Auto-detects SQLite vs Postgres. `get_db` is the dependency that hands each request a database session. |
| `auth.py` | Password hashing (bcrypt), JWT creation/decoding, and `get_current_user` — the dependency that protects endpoints by requiring a valid token. Plus `get_current_user_optional` (OAuth2 with `auto_error=False`), which returns the signed-in user **or `None`** and never raises — deliberately a second function rather than a flag on the first, because one dependency that sometimes 401s and sometimes returns `None` is exactly the ambiguity that leaks. It exists for `GET /recipes/browse`, which must stay readable without an account yet still honour a block for a signed-in reader. |
| `models/` | **ORM models** — Python classes mapping to database tables. Eighteen, one file per table (the two newest, `push_subscription` and `prompt_send`, are documented in CLAUDE.md's model list and in their own docstrings rather than repeated here): `user` (carries `profile_visibility` — `public`/`private`, default private — which picks the create-form default and drives the bulk sweep, but does **not** gate reads; and `photo_url` — a nullable Cloudinary URL for the profile picture, NULL → the first-letter monogram; a face beside a name is identity, not private content, so it is not gated by `profile_visibility`; plus `last_feed_seen_post_id` — #97's feed read-mark, an ID rather than a timestamp because SQLite's second-granular `created_at` would mis-count a same-second post, and NOT a foreign key because a FK would `SET NULL` on post deletion and reset the user to "never looked"; plus the six #89 notification columns: `timezone` (nullable — every account predating #89 has none, and a user with none is never due for anything), `notify_hour` (18), `notify_prompt` / `notify_people` (both true), `quiet_from` (22) and `quiet_to` (8)), `recipe` (carries `origin_attribution` — the byline — and `visibility`, a concrete 3-value setting: `public` \| `friends` \| `private`), `ingredient`, `ingredient_section`, `step` (carries `voice_note`, a plain `Text` column holding the typed note for that step — **not audio**, see below), `cook_event` (carries `note` — a cook's variation), `handoff` (carries `token` — a capability secret for the invite link), `feedback` (an in-app feedback note), `password_reset` (time-limited token for the forgot-password flow), `friendship` (symmetric friend graph — one row per unordered pair, `state` pending|accepted; the social feed's Phase-0 primitive), `post` (a shared meal for the presence feed — `photo_url` + `dish_name`, an optional `description`, an optional `recipe_id` linking a recipe the author owns, and its own concrete 3-value `visibility` like a recipe's; carries no ingredients/steps), `recipe_request` (#79 — an ask on a post: `post_id` + `requester_id` both CASCADE, `state` pending|fulfilled, **UNIQUE(post_id, requester_id)** so asking twice is one row and a fulfilled row is re-opened rather than blocking a re-ask), `notification` (the inbox: `user_id` recipient + `actor_id` CASCADE, nullable `post_id`/`recipe_id` refs **`ondelete=SET NULL`** so a notification outlives its subject instead of vanishing, `read_at` nullable = unread), `recipe_save` (a bookmark — this user keeps this recipe, #57: ONE recipe FK, no relation column, no copy; see the guardrails in the model docstring), `block` (#85 — `blocker_id` + `blocked_id`, both CASCADE and indexed, **UNIQUE(blocker_id, blocked_id)** declared inline in `create_table` because SQLite has no ADD CONSTRAINT and the chain must replay there. The **row is directional; the effect is symmetric** — `is_blocked` matches either order — so two rows can legitimately exist for one pair and unblocking removes only your own), `report` (#87 — `reporter_id` + `reported_user_id` both CASCADE, `reason` from a five-name vocabulary, an optional free-text `note` from the reporter, and `state` open|closed. Both FKs CASCADE where `notification`'s SET NULL: a notification is a message someone already read and should outlive its subject, while a report is a live case about a specific pair and is moot if either account is gone. **No unique constraint**, deliberately — the rule is "one OPEN report per reporter per target", whose state predicate a constraint can't express, so the router dedupes in Python exactly as `notify()` does). |
| `schemas/` | **Pydantic models** — define the JSON shape of requests and responses, separately from the DB models. Keeps internal fields (like password hashes) from leaking to the API. Also where every **field ceiling** lives: `schemas/recipe.py` declares the `Text40`..`Text4000` aliases and the `MAX_INGREDIENTS` / `MAX_STEPS` / `MAX_SECTIONS` collection caps. Recipes had NO limit at all until #100 — not in the schema and not on the column, since `Mapped[str] = mapped_column()` infers an unlimited VARCHAR — so one request could put a megabyte in a dish name and every card in Browse would try to render it. The caps are deliberately generous (a dish name is 120, matching a post's; a story is 4000) because they exist to refuse abuse and protect the layout, not to edit anyone: there are no character counters in the UI, and create and edit share the same ceilings exactly — an edit accepting less than a create would make an already-saved recipe unsavable. |
| `routers/` | **Endpoint definitions**, grouped by domain: `auth` (signup/login/me, plus `PATCH /auth/me` to edit name/email/password/profile picture (`photo_url`)/profile visibility and the six #89 notification settings (`timezone`, `notify_hour`, `notify_prompt`, `notify_people`, `quiet_from`, `quiet_to` — `timezone` arrives from the client on every login and signup, since the nudge fires in the recipient's local time and a user with no zone is never due), `DELETE /auth/me` to delete account, `POST /auth/forgot-password` and `POST /auth/reset-password` for the email-based password-reset flow — signup also auto-accepts pending recipe invites addressed to the new user's email), `recipes` (CRUD + scaling + browse + cook + handoff, plus sharing: `/recipes/shared` and `/recipes/handoffs/{id}/accept`, plus the invite flow: `GET /recipes/invite/{token}` — unauthenticated *full* read of a handed-off recipe; `POST /recipes/invite/{token}/claim` — authenticated grant claim by token), `upload` (Cloudinary photos — `POST /upload/recipe-photo` for a recipe cover/step and `POST /upload/avatar` for a profile picture, a square face-centered crop), `feedback` (in-app feedback notes, self-scoped), `friends` (the symmetric friend graph: request/accept/remove, list, incoming requests, handoff-seeded suggestions, the app-wide directory `GET /friends/discover` (+ `?q=` name search — everyone bar you/your friends/pending/**blocked**, #80), a read-only `GET /friends/profile/{id}`, **blocking** (#85: `POST`/`GET`/`DELETE /friends/blocks`) and **reporting** (#87: `POST /friends/reports` — the other half of blocking, and the one route in this file that deliberately does NOT consult `is_blocked`, in either direction: gating it would make a harasser unreportable the moment they block their victim. Silent to the reported person, one open report per reporter per target, and no read endpoint at all) — social feed Phase 0. FIVE of these enforce the block BY HAND — `request_friend`, `accept_friend`, `friend_suggestions`, `discover_people` and `user_profile` — because they return *people* rather than recipes or posts and so have no `can_view` to lean on. `friend_suggestions` is the one most easily missed: it is seeded from the handoff graph and a block deliberately preserves handoffs, so without an explicit filter the person you blocked reappears as a suggestion BECAUSE you once handed them a recipe). `recipes` also carries `POST /recipes/parse`, which structures a spoken/pasted recipe into fields via an LLM and saves nothing, and `GET /recipes/invite/{token}/preview`, which serves crawler-only OpenGraph HTML so a shared invite link unfurls as the actual recipe (see `services/invite_og.py`), plus two self-scoped autosuggest reads (`GET /recipes/ingredient-suggestions`, `GET /recipes/field-suggestions` — the caller's own past ingredients / sources + cuisines). `posts` (the presence feed — `POST /posts` to share a meal, `GET /posts/feed` (`?scope=friends|everyone` — friends-plus-own, or public posts from non-friends; since #94 `everyone` is the client's COLD-START fall-through, not a user-facing toggle), `GET /posts/browse` (still served and tested; **no client calls it** since #94 removed Browse's Meals tab), `GET /posts/{id}`, `PATCH /posts/{id}` and `DELETE /posts/{id}` (both author-only, both 404 rather than 403 for anyone else, so neither confirms the post exists to someone not entitled; PATCH edits exactly three fields — dish name, description, visibility — and deliberately not the photo, the attached recipe, the author, or the #97 read-mark), `GET /posts/users/{id}` for a profile grid, `POST /posts/feed/seen` (the feed read-mark, #97), and the request loop (`POST`/`DELETE /posts/{id}/request`, `GET /posts/requests/incoming`, `POST /posts/{id}/fulfill` — #79); reuses `services/friends.py`, no new service). `recipes` also carries the KEEP surface (#57): `POST /recipes/{id}/save` and `DELETE /recipes/{id}/save` (bookmark a recipe you can read — gated on `can_view`, so keeping can never widen access — and remove your own bookmark), plus `GET /recipes/kept`, the shelf that merges recipes handed to you with ones you kept and re-checks `can_view` per row. `recipes` also carries `GET /recipes/users/{id}` — a user's recipes for their profile grid, `can_view`-gated (own → all; friend → `public` + `friends`; non-friend → `public` only), the recipe counterpart of `GET /posts/users/{id}`. `notifications` (the inbox, #79 — `GET /notifications`, the caller's own rows keyset-paginated on id and returning `unread_count` alongside them, and `POST /notifications/read`. It was a READER only until #89 added the push surface (`GET /notifications/vapid-key`, `POST`/`DELETE /notifications/subscribe`, `POST /notifications/subscribe/rotate`, `POST /notifications/run-daily-prompt`); the inbox half is still read-only, because every notification is produced by `services/notifications.py`'s `notify()`, called from whichever router performed the act. Its one piece of real logic is the anonymity pass — for any type in `ANONYMOUS_TYPES` (today just `recipe_kept`, #96) it nulls every actor field on the way out, so the row can store `actor_id` for `notify()`'s own dedupe and never-notify-yourself checks while the cook reads "Someone kept your Adobo"). `main.py` also serves an unauthenticated `GET /health` (liveness) and `GET /health/ready` (the ALB's target, which proves the task can reach the database — **memoized for 10 minutes on success**, because the ALB polls it every 30s and an unmemoized DB query every 30s kept Neon's compute awake 24/7 and burned the whole monthly allowance on health checks; a new task and any failure always re-probe, so deploy-time rollback still works). **65 routes total** across **7 routers** — count them with `grep -rn "^@router\.\|^@app\." app/`; the full table is in `README.md`. |
| `services/` | **Business logic**, decoupled from HTTP. `scaling.py` (the precise/imprecise/unmeasured quantity math), `folk_units.py` (the folk/body/vessel unit vocabulary — see below), `growth.py` (`soul_count`, `growth_stage`, `growth_vitality` — still computed and returned on `RecipeResponse`, but **no UI displays them** since the garden was removed), `sharing.py` (`can_view` for recipes and `can_view_post` for posts — the single read-authorization rule per resource type, sharing one truth table in `_resource_is_visible`. In evaluation order: **a block between viewer and owner in either direction → never visible, checked FIRST so that it beats `public`** (a block that didn't outrank `public` would leave every public recipe and post of theirs on your screen); then viewable if owner **or** the item is `public` **or** it is `friends` **and** the viewer is an accepted friend (`are_friends`) **or** — recipes only, orthogonally — they hold an accepted handoff grant, **which a block deliberately does NOT override** (see `blocks.py` below). Both functions take optional precomputed `is_friend` / `blocked` (and `is_grantee` for recipes) so a list endpoint can answer once for a page instead of once per row — callers may pass the *answer*, never a second copy of the logic. Plus `effective_visibility`, which returns the recipe's own concrete `visibility` unchanged — the profile is not consulted at read time; Browse simply shows recipes whose `visibility == "public"`). `quantity.py` (server-side classification of a written amount into precise/imprecise/unmeasured, sharing the `folk_units` vocabulary so the model's output is graded by the app, not by the model). `recipe_ai.py` (the OpenRouter call behind `POST /recipes/parse` — a strict-schema extraction that preserves imprecise amounts verbatim and falls back to a local parser when unavailable). `email.py` (sends password-reset emails via AWS SES). `invite_og.py` (pure builders for the invite link-preview OpenGraph card served by `GET /recipes/invite/{token}/preview` — HTML-escaped, POSITIONING-guarded, unit-tested without HTTP). `blocks.py` (#85 — `is_blocked(a, b, db)`, true if either has blocked the other and false when an id is `None` or both are the same person, plus `blocked_ids(user_id, db)` for list endpoints. The third single-predicate service, alongside `can_view` and `are_friends`: one place answers "are these two blocked?". The one asymmetry worth knowing before you "fix" it — a block outranks visibility but **not** an already-accepted handoff grant, because you genuinely handed that person that recipe and a block means "no new contact", not "unsend". A *new* grant can't cross a block; `handoff_recipe` refuses with the same 404 an unknown user gets). `push.py` (#89 — the ONE place a notification leaves the building: RFC 8292 VAPID signing plus RFC 8291 aes128gcm encryption, built on `cryptography` and `httpx`, both already pinned. **No new dependency**: the obvious choice, `pywebpush`, hard-depends on `requests` while this codebase standardised on httpx. Hand-rolled crypto fails SILENTLY, so `tests/test_push.py` DECRYPTS what it produces from the receiver's side — that round trip caught a real bug where the content key was derived from a zero salt while the header carried the random one, a body no browser could ever have read. It DEGRADES rather than raising: with no keypair configured, `is_configured()` is False and every send is a logged no-op, so a deploy without the secret behaves exactly as it did before push existed — deliberately unlike `email.py`, which raises and leans on its one HTTP caller, a pattern that would make a scheduled job fail silently. Only **404 and 410** mean a dead subscription; pruning on any 4xx would empty the table on the first botched key rotation, and a subscription can only be recreated by the user re-granting on that device. Also `in_quiet_hours`, whose window WRAPS MIDNIGHT in the default 22→8 configuration — the obvious `from <= h <= to` is exactly backwards there — and which reads equal bounds as "no quiet hours" rather than a 24-hour blackout). `prompt.py` (#89 — who is due, and what the nudge says. The count is the careful part: the obvious `COUNT(*) WHERE user_id IN (friends) AND id > mark` mirrors the feed's own SQL, which is the trap, because the feed's correctness lives in a Python `can_view_post` filter two lines later — that aggregate would put a friend's PRIVATE post and a BLOCKED person's post into a push notification. It counts DISTINCT authors, not posts, since the copy says "3 friends posted", and zero sends NOTHING, like every other absence in this app. `is_due` asks "has their hour PASSED today" rather than "is it exactly their hour", because no trigger is on-time — and `prompt_sends`' UNIQUE (user, local_date) is what makes that catch-up safe). `friends.py` (`notifications.py` is the SINGLE producer of a notification — `notify()` validates the type against a vocabulary, never notifies you of your own act, optionally dedupes against an identical unread row (which is what stops an ask/retract loop flooding a cook's inbox), and **deliberately does not commit** so it lands in the caller's transaction; plus `unread_count` and `mark_read`. `are_friends` — the single friendship predicate every friends-gated surface funnels through, like `can_view` for recipes — plus `existing_friendship` / `friend_ids`). |

**Folk units, and why scaling has three cases rather than two.** `folk_units.py`
holds the vocabulary of units that name a *vessel* or a *gesture* instead of a
measurement, and splits it in the one way that matters at scale time:

- **Countable** (`FOLK_UNITS`) — the vessel is unknowable but the count is real.
  "3 soup spoons" doubled genuinely is "6 soup spoons", and `FOLK_PLURALS` makes
  it read like a person wrote it ("2 knobs of butter", not "2.0 knob").
- **Non-linear** (`NON_LINEAR_UNITS`) — the number is a geometry, not a quantity.
  "3 fingers of water" is a depth in the pot; doubling the rice widens the pot,
  so the depth barely moves. These are kept verbatim and the cook is handed the
  multiplier (`scale_note`) to apply by feel.

Anything else imprecise scales but is marked `(approximate)` rather than posing
as a measurement. `frontend/src/utils/quantity.js` uses the same vocabulary to
classify an amount as imprecise at *entry* time; the two lists must stay in sync.

**Sharing model (the "Shared" tier).** Passing a recipe *is* sharing — there is no separate access-grant concept. The `handoffs` table doubles as the grant: passing a private recipe to someone creates a `Handoff` on **that recipe**, with `state` in `pending | accepted` and a `token` (a `secrets.token_urlsafe(32)` capability secret). In-app recipients are accepted instantly; email invites stay `pending` until that address signs up (then they auto-accept). Additionally, any holder of the invite token can **claim** the grant (via `POST /recipes/invite/{token}/claim`) — this resolves the mismatched-email orphan case (an invite addressed to one email claimed by someone who signed up with another). `can_view` in `sharing.py` is the single rule every recipe read funnels through (`get_recipe`, scale, cook, handoff) — keep it that way; a second, subtly different rule elsewhere is how private recipes leak. `GET /recipes/shared` lists a user's accepted-grant recipes; `RecipeResponse.shared_with_count` tells an owner how many people a private recipe is shared with (count only — no identities).

**Read is not write.** A grantee gets **view + cook only**. They cannot edit or delete the owner's recipe, and cannot re-share it: `patch_recipe` and `delete_recipe` both filter `Recipe.user_id == current_user.id` (so a non-owner gets a 404), and `handoff_recipe` requires ownership too. `can_view` deliberately does not answer "may edit" — that question is settled separately, in the router. Nothing in this app lets a recipient add to a recipe they were sent; keeping and cooking it is the whole promise.

**The invite read is open — the token is the capability.** A recipient holding an invite link (`/invite/:token`) reads the **full** recipe with no account: ingredients, sections, steps and their per-step remarks, the story, servings, description, cuisine, cover photo. This was formerly a soft wall (name/story/photo only, signup required to see an ingredient), which inverted the point — the person on the far end of a handoff has never tasted the dish and wants to cook it. The `token` is a `secrets.token_urlsafe(32)` capability secret; holding the link *is* the permission to read. What the `InvitePreview` schema still withholds is the *account*, not the dish: the owner's private `notes` scratchpad and any user/author ids. Signing up is what unlocks keeping and cooking it — **never** editing or adding to it, which stays owner-only (`patch_recipe`/`delete_recipe` filter on `user_id`) — and after signup/login the token is claimed and becomes a durable grant.

**Models vs Schemas — the distinction that trips people up.** A *model*
(`models/recipe.py`) is the database table. A *schema* (`schemas/recipe.py`) is
the API contract. They look similar but serve different masters: the model has
every column (including ones you never expose); the schema has only what the API
should accept or return. `RecipeCreate` (what you send to create) and
`RecipeResponse` (what you get back) are different schemas for the same model.
`RecipeResponse` also includes derived values (`cook_count`, `owner_cook_count`,
`last_cooked_at`, `shared_with_count`, `soul_count`, `growth_stage`,
`growth_vitality`) that are computed per-request in `_attach_growth_fields`. Plus `keeper_count` (#96) — how many people keep this recipe, populated by a SEPARATE helper (`_keeper_count`, not `_attach_growth_fields`) and **only for the owner**: `None`, never `0`, for anyone else, so no other client is handed a number it could render. There is no keeper LIST anywhere, for anyone, including the cook, not
stored columns. The frontend uses some of these (e.g. `cook_count`); the
`growth_*` / `soul_count` fields are computed but no longer displayed since the
garden UI was removed. There are no `child_count` or `has_grandchildren` fields —
those were lineage counts and went with the tree.

**`alembic/`** (sibling of `app/`, not inside it) — database migrations. Every
time a model changes (new column, etc.), you generate a migration here and apply
it to keep the real database schema in sync. Files in `alembic/versions/` are
the ordered history of schema changes.

## Frontend (`frontend/`)

A **React** app built with **Vite** (the dev server + build tool) and styled
with **Tailwind CSS**. If React is new to you, the mental model is:

- The UI is built from **components** — JavaScript functions that return markup
  (JSX, which looks like HTML inside JS). A page is just a big component made of
  smaller ones.
- Components hold **state** with the `useState` hook (a "hook" is a function
  starting with `use` that plugs into React's features). When state changes,
  React re-renders that component automatically. You never manually touch the
  DOM.
- `useEffect` runs code *after* render — used here mostly to fetch data from the
  backend when a page first loads.

### How a page actually loads (the data flow)

1. The browser loads `index.html`, which loads `main.jsx`.
2. `main.jsx` wraps everything in `<BrowserRouter>` (enables URL routing) and
   renders `<App>`.
3. `App.jsx` looks at the current URL and renders the matching **page**
   component (e.g. `/my-recipes` → `MyRecipes.jsx`).
4. That page, on mount, calls the backend via `client` (axios) — e.g.
   `client.get('/recipes')`.
5. The response data goes into component **state**; React renders the list.

### Key files

| File | What it does |
|---|---|
| `main.jsx` | The true entry point. Mounts the app and enables routing. You rarely touch this. |
| `App.jsx` | The **route table**, plus exactly two fire-and-forget calls on mount: `reconcile()` (#90 — sync the cached identity against the server, once per app start) and `registerServiceWorker()` → `reconcileSubscription()` (#89 — register the push worker for everyone signed in or not, then re-bind this browser's subscription to whoever is signed in, which is the shared-phone fix). | `api/client.js` | A single configured **axios** instance — the *only* thing that talks to the backend. ### Conventions to follow

- **Auth storage:** JWT in `localStorage` under `issei_token`; the user object
  under `issei_user`.
- **All API calls go through `src/api/client.js`** — never call `fetch`/axios
  directly, or you lose the token attachment and 401 handling.
- **Function components + hooks only** — no class components.
- **Tailwind only** — no UI libraries. Use the design tokens in
  `tailwind.config.js` (`cream`, `card`, `line`, `ink`, `ink-soft`, `terra`,
  `plum`, `saffron`, `peach`, `sage`, `brick`, `action`) rather than raw hex.
  That list is the WHOLE palette — `coral`, `mint`, `periwinkle`, `paper`,
  `herb`, `growth` and `soil` were deleted, and Tailwind emits nothing at all
  for a colour it doesn't know, so referencing one renders as no fill, silently.
  It has shipped that way three times; `src/palette-usage.test.js` now fails on
  any reference to a colour the config doesn't define.
- **Two typefaces, both loaded** — `font-display` (Fraunces) for headings and
  most UI, `font-sans` (Nunito Sans) for body. Those are the only two families
  in `index.html`. **There is no `font-hand`**: Caveat, Shantell Sans, Patrick
  Hand, Architects Daughter and Kalam were each tried for the story and the step
  notes and all five were cut — it's content someone cooks from (a legibility
  cost paid for a mood), and the data is typed text, so a script face implies a
  recording that doesn't exist. A person's presence is signalled *structurally*
  instead: the saffron card, the quote stamp, the attributed heading, Fraunces
  italic. (`font-serif`/Cormorant Garamond does still exist as a key, but it is
  legacy and deliberately **not loaded** — don't use it.)
  `tailwind.config.test.js` pins these invariants: no `hand` family, and every
  family the app references must actually be loaded in `index.html` — a
  referenced-but-unloaded font falls back to a system face and fails silently.
- **Mobile-first**, max-width 430px centered.

## The two halves, connected

```
Browser ──────────────── Server ──────────── Database
React app                FastAPI app          Postgres (Neon)
(frontend/)              (app/)               via SQLAlchemy
   │                        │
   │  client.js (axios)     │  routers → schemas → services → models
   └──── HTTP/JSON ─────────┘
        e.g. GET /recipes
        Authorization: Bearer <JWT>
```

- The frontend never touches the database. It only makes HTTP calls.
- The JWT (issued at login) rides along on every request so the backend knows
  who you are.
- Local dev: frontend on `localhost:5173`, backend on `localhost:8000`. CORS in
  `main.py` allows that origin to call the API.

## Development notes

- **Backend changes that touch the database** (new/changed model fields) need an
  Alembic migration *and* application to the production database — these aren't
  automatic. Watch for them when reviewing changes.
- **Two servers must be running to use the app locally**: `uvicorn app.main:app
  --reload` (backend) and `npm run dev` in `frontend/` (frontend).
- **Verifying changes:** backend has `pytest` (**600 tests** across `tests/`);
  frontend has Vitest + React Testing Library (**821 tests in 55 files**) — run
  `npm test` (`vitest run`) in `frontend/`. `npm run build` still catches
  syntax/import errors. These counts move; re-run both suites rather than
  quoting a number from a doc.
- **A note on honesty in docs.** Several rounds of feature *removal* (the garden
  UI, remix, the shopping list, `services/units.py`, the whole lineage model)
  left these documents describing an app that no longer existed. When you remove
  something, correct `README.md`, `ARCHITECTURE.md`, `FUTURE.md` and `CLAUDE.md`
  in the same pass, and check the explicit don't-claim list in `POSITIONING.md`.
  The two standing traps: **there is no audio in this product** (`voice_note` is
  a typed `Text` column, so never write "voice", "recording" or "in their own
  words" in user- or recruiter-facing text), and **recipes do not form trees**.
