## What This Is

A deployed full-stack app (FastAPI backend + React frontend) for **sending one recipe from the person who cooks it to the person who just tasted it and asked for it** — *issei* (一世) = "first generation." Someone cooked you something you'd never had before; this is how they send it to you. A recipe is attributed to a *person* (the dish is the title, the person is the byline "from Lola"); imprecise measurements like "a dash" or "3 soup spoons" are preserved verbatim as fidelity, never normalized; per-step notes carry the knowledge an ingredient list can't hold; and the recipient reads the whole thing from a capability link with no account. The signature is **that handoff** — the fuzzy-quantity model is the supporting layer that makes what arrives honest. The UI is a warm, playful "kitchen" (bold sticker / color-block design). Backend on AWS ECS Fargate, frontend on Vercel, PostgreSQL (Neon) in production, SQLite locally.

> **Read `POSITIONING.md` before writing any user-facing or recruiter-facing copy.** It holds the one-liner and an explicit list of claims that are FALSE and must not appear anywhere. The three that keep resurfacing:
> 1. **No audio, ever.** `Step.voice_note` is a `Text` column typed by whoever wrote the recipe down. Never write "voice", "recording", "audio", "listen", or "in their (own) words" in UI copy or docs. Six test files assert this (DictateButton, PasteRecipe, RecipeBody, Login, Welcome, InviteLanding — see POSITIONING.md for what each checks).
> 2. **No lineage / family tree.** Removed in `8a3b734`. No ancestors, descendants, roots, branches, subtrees, or child counts.
> 3. **A recipient cannot edit.** `patch_recipe`/`delete_recipe` filter on `user_id`. Read is not write.

> **Garden → kitchen history:** an earlier UI rendered recipes as plants growing seed→sprout→sapling→tree and the Kitchen as a garden of them. That UI was removed and replaced by the current kitchen design. The backend still *computes* `growth_stage`/`growth_vitality` (`services/growth.py`) but the frontend no longer displays them. The garden UI and its docs were removed once the kitchen design was locked in; they remain in git history.

## Architecture

**App entry:** `app/main.py` — mounts seven routers (auth, recipes, upload, feedback, friends, posts, notifications) and a `/health` endpoint.

**Routers** (`app/routers/`) — endpoint definitions. Each router handles one domain: auth (signup/login/me — `login` now also returns `profile_visibility` and `photo_url` — plus `PATCH /auth/me` to edit name/email/password/profile_visibility/photo_url (all but email+password need no password — low-risk; `photo_url` is validated to a Cloudinary HTTPS host, or blank → NULL/monogram), `DELETE /auth/me` to delete the account, and the password-reset pair `POST /auth/forgot-password` / `POST /auth/reset-password`), recipes (CRUD + scaling), upload (Cloudinary photos — `POST /upload/recipe-photo` and `POST /upload/avatar`, the latter a square 400x400 face-gravity crop into `issei/avatars`), friends (the symmetric friend graph — social feed Phase 0). Recipes also has the sharing actions: `POST /{id}/cook`, `POST /{id}/handoff`, `GET /recipes/shared`, `POST /recipes/handoffs/{id}/accept`, the invite flow (`GET /recipes/invite/{token}` — unauthenticated **full** recipe read; `POST /recipes/invite/{token}/claim`; `GET /recipes/invite/{token}/preview` — crawler-facing OpenGraph HTML so a shared link unfurls as the recipe, see `services/invite_og.py`), plus the KEEP surface (#57): `POST /recipes/{id}/save` / `DELETE /recipes/{id}/save` (bookmark a recipe you can already read — gated on `can_view`, so keeping never widens access — and drop your own bookmark) and `GET /recipes/kept` (the shelf: recipes handed to you MERGED with ones you kept, each re-checked through `can_view`, plus an `unreachable_count` for ones the cook has since restricted or deleted). Note `can_view` must NEVER consult saves — a save row is reader-created, so trusting it would be a self-grant; `services/sharing.py` does not import `RecipeSave`. Recipes also has the **optionally-authenticated** `GET /recipes/browse` (anonymous is fine — it's the app's one unauthenticated JSON feed — but a signed-in viewer is resolved via `get_current_user_optional` so their blocks are honoured; it was the one public surface a block couldn't otherwise reach), and `GET /recipes/ingredient-suggestions` / `GET /recipes/field-suggestions` (the caller's own past ingredients / sources+cuisines for form autosuggest, self-scoped). Friends has `POST /friends/request`, `POST /friends/{id}/accept` (addressee-only), `DELETE /friends/{id}`, `GET /friends` (accepted friends; optional `?order=active` sorts by each friend's most-recent *visible* post — the Feed presence strip #75 — vs the default `recent` = friendship recency for the Friends page), `GET /friends/requests`, `GET /friends/suggestions` (seeded from the handoff graph), `GET /friends/discover` (the app-wide directory + `?q=` name search — everyone except you, your ACCEPTED friends and anyone in a block relationship with you. Someone the caller has ASKED deliberately STAYS listed, carrying `friend_state` (`none` | `requested`) so the row reads "Requested" instead of the person silently vanishing — which a real user read as "did that work, or did I just remove them?". An INCOMING request is hidden instead, because it already has a home in `GET /friends/requests` (rendered above this section on the Friends page) and listing it here too showed one request twice with two live Accept buttons. No `friendship_id` is returned at all — no directory row has an action that needs one. The 50-row cap applies ONLY to addable strangers; anyone you asked is returned outside it, so the cap can never drop the person the label exists to keep; #80's fix for "I can't find how to add people". Discloses name+photo to any signed-in user, which `/u/{id}` already did — what's new is that it's ENUMERABLE. Deliberately NOT gated on `profile_visibility` (never consulted at read time, and private by default → an empty list); email is not searchable. Declared before `/profile/{id}` so the literal path isn't read as a user id), `GET /friends/profile/{id}` (read-only profile — returns the target's `profile_visibility`, `photo_url`, recipe and post counts the caller may see (gated by the visibility model), and `friend_count` (a symmetric public number, NOT caller-gated)), and the BLOCK surface (#85): `POST /friends/blocks` (block someone — mutual invisibility from then on; also deletes the friendship, drops pending asks both ways, and clears notifications between the two, all in one transaction), `GET /friends/blocks` (only who YOU blocked — never who blocked you, which would turn a protection into a notification, and the only route back since a blocked profile 404s) and `DELETE /friends/blocks/{user_id}` (removes just your own row; does NOT restore the friendship). Four friends endpoints enforce the block BY HAND because they return people rather than recipes/posts and so have no `can_view` to lean on — `discover_people`, `user_profile`, `request_friend` and `friend_suggestions`; the last is the easiest to miss, since it's seeded from the handoff graph and a block deliberately preserves handoffs, so without an explicit filter the person you blocked reappears as a suggestion BECAUSE you once handed them a recipe. The friends list / requests / suggestions also carry each person's `photo_url`. Posts (the presence feed — social feed Phase 1a) has `POST /posts` (share a meal: photo + dish name, optional description, optional link to a recipe you own), `GET /posts/feed` (newest first, keyset-paginated via `?before_id=`; no like button; `?scope=friends|everyone` — `friends` (default) = accepted friends' posts + your own, `everyone` = **public** posts from people you're NOT friends with (discovery, #70), scoped in SQL to `visibility == "public"` so a stranger's friends/private post can't leak), `GET /posts/browse` (public posts for Browse's Meals tab #71 — every `visibility == "public"` post, newest first, uncapped so the client can search the full set; the post counterpart of `GET /recipes/browse`, and unlike the everyone-feed it includes own+friends' public posts), `GET /posts/{id}` (author, a friend of the author, **or anyone on a public post** — that's how a public meal opens from Browse's `/posts/:id` page; else 404), `DELETE /posts/{id}` (author-only), `GET /posts/users/{id}` (a user's posts for their profile grid, friend-or-own gated). The feed/single/profile responses null a post's `recipe_id` when the viewer can't read that linked recipe (private or soft-deleted), so a "See the recipe" link never dead-ends, and carry the post author's `author_photo_url` for the avatar. Recipes also has `GET /recipes/users/{id}` — a user's recipes for their profile grid, `can_view`-gated (own → all; friend → `public` + `friends`; non-friend → `public` only), the recipe counterpart of `GET /posts/users/{id}` (both power the tabbed `ProfileContent`). Posts also carries the request loop (#79): `POST /posts/{id}/request` (ask the cook — open to **anyone who can `can_view_post` the post**, deliberately not friends-only, and only where the caller can't already read a recipe for it; a fulfilled row is re-opened rather than silently blocking a re-ask, and the cook's notification is deduped while unread so an ask/retract loop can't flood the inbox), `DELETE /posts/{id}/request`, `GET /posts/requests/incoming` (the cook's asks + who asked — the only place a requester's NAME is returned; the COUNT also reaches the author on their own posts via `request_count`, which stays `None` for every other viewer), and `POST /posts/{id}/fulfill` (author-only, own-recipe-only; mints an accepted `Handoff` per pending requester, so a **private** recipe is delivered without its visibility changing). Posts also carries the feed read-mark (#97): `POST /posts/feed/seen` advances `User.last_feed_seen_post_id` to the newest post the caller has seen, and `GET /posts/feed` returns `is_new` per post so the client can draw a "You're all caught up" divider. **`is_new` is a FLAG, never a FILTER** — the feed returns exactly the same posts either way, and nothing expires: a post is the top of the funnel to a handoff, so a vanishing post would take the ask with it. The mark is an **id, not a timestamp** (`created_at` is second-granular on SQLite, so a same-second post would be wrongly counted read — the same reason feed pagination is keyset on `id`), it moves **forward only**, and it is NOT a foreign key (a FK would `SET NULL` when that post is deleted, resetting the user to "never looked"). Your own post is never `is_new` to you, and `is_new` is `None` off the feed — Browse, a permalink and a profile grid have no concept of new. It is also the prerequisite for #89: "3 friends posted since you last looked" is the whole content of a push prompt and could not be computed before this. Notifications has `GET /notifications` (the caller's inbox, keyset on id, returning `unread_count` with the rows) and `POST /notifications/read`. `main.py` also serves `GET /health` and `GET /health/ready`. **58 routes total** — this number has changed several times; re-count with `grep -rn "^@router\.\|^@app\." app/` rather than trusting it.

**Models** (`app/models/`) — **fifteen** SQLAlchemy ORM models: `user` (carries `profile_visibility` — `public | private`, default private — which picks the create-form default and drives the bulk sweep, but does **not** gate reads; and `photo_url` — a nullable Cloudinary URL for the profile picture, NULL → the first-letter monogram; not gated by `profile_visibility`), `recipe`, `ingredient`, `ingredient_section`, `step`, `cook_event`, `handoff`, `feedback`, `password_reset`, `friendship` (symmetric friend graph, one row per unordered pair — social feed Phase 0), `post` (a shared meal for the presence feed — photo + dish name, optional description, optional link to a recipe the author owns, its own concrete 3-value `visibility` with `server_default "friends"`; no ingredients/steps — social feed Phase 1a), `recipe_request` (#79 — an ask on a post; unique on (post, requester), `state` pending|fulfilled), `notification` (the inbox — recipient + actor + nullable post/recipe refs that `SET NULL` so a notification outlives its subject, `read_at`), `user` also carries `last_feed_seen_post_id` (#97 — the feed read-mark; see the routers note), `recipe_save` (#57 — a BOOKMARK: this user keeps this recipe. ONE recipe FK (a second would be `parent_recipe_id` renamed), no relation/kind column (that would be `lineage_relation`, whose removed enum contained "kept"), no keeper counts anywhere, and never consulted by `can_view`), `block` (#85 — `blocker_id` + `blocked_id`, unique on the pair. The ROW is directional, the EFFECT is symmetric: `is_blocked` matches either order, so two rows can legitimately exist for one pair and unblocking removes only your own). Key relationship: Recipe → IngredientSection → Ingredient, but ingredients also have a direct `recipe_id` FK (deliberate denormalization for query simplicity). Recipe also carries `visibility` (concrete: `public | friends | private`), `origin_attribution` (the byline) and `prompt_*`. **No `parent_recipe_id`, no `lineage_relation`, no `ghost_ancestor` table** — all dropped with the lineage model (migration `c1d2e3f4a5b6`).

**Schemas** (`app/schemas/`) — Pydantic models for request/response validation. Separate from ORM models to control what's exposed at the API boundary.

**Services** (`app/services/`) — business logic decoupled from HTTP layer. Eleven: `scaling.py` handles the three-type quantity model (precise/imprecise/unmeasured), `folk_units.py` holds the folk-unit vocabulary, `quantity.py` classifies a written amount into that model (shared vocabulary with `folk_units`), `recipe_ai.py` is the OpenRouter call behind `POST /recipes/parse` (strict-schema extraction, amounts preserved verbatim, falls back to a local parser when unavailable), `growth.py` computes `soul_count`/`growth_stage`/`growth_vitality` (still computed + returned on `RecipeResponse`, but no longer surfaced in the UI since the garden redesign), `sharing.py` (formerly `lineage.py`) holds `can_view` (recipes) and `can_view_post` (posts) — the two single read-authorization rules — sharing one truth table (`_resource_is_visible`). In evaluation order: **a block between the two in EITHER direction → never visible, checked FIRST so it beats `public`** (a block that didn't outrank `public` would leave every public recipe and post of theirs on your screen); then owner OR `public` OR (`friends` AND the viewer is an accepted friend via `are_friends`) OR — recipes only, orthogonally — an accepted handoff grant, **which a block deliberately does NOT override** (you gave them that dish; a block stops new contact, not what's already handed over — though a NEW grant can't cross a block, `handoff_recipe` refuses). Both take optional precomputed `is_friend`/`blocked` so a list endpoint answers once per page instead of once per row; plus `effective_visibility`, which returns the recipe's own concrete `visibility` unchanged (the profile is not consulted at read time; Browse shows recipes where `visibility == "public"`), `email.py` sends the password-reset email via AWS SES, `invite_og.py` builds the crawler-facing OpenGraph card for `GET /recipes/invite/{token}/preview` (so a shared invite link unfurls as the actual recipe), and `notifications.py` is the single producer of a notification (`notify()` — validates the type, never notifies you of your own act, dedupes against an identical unread row, and deliberately does NOT commit so it lands in the caller's transaction), `blocks.py` holds `is_blocked` (either direction; False for a None id or for one person against themselves) and `blocked_ids` (the bulk set for list endpoints) — the third single-predicate service, and `friends.py` holds `are_friends` — the single friendship predicate (like `can_view`), for the symmetric friend graph.

**Auth** (`app/auth.py`) — JWT-based stateless auth. `get_current_user` is the dependency injected into protected endpoints. `get_current_user_optional` (OAuth2 with `auto_error=False`) returns the signed-in user **or None** and never raises — a deliberately separate function rather than a flag, because one dependency that sometimes 401s and sometimes returns None is the ambiguity that leaks. It exists solely for `GET /recipes/browse`, which must stay readable without an account yet still honour a block.

**Migrations** (`alembic/`) — `alembic/env.py` imports all models and uses the app's engine directly. New models must be imported there for autogenerate to detect them.

## Key Design Decisions

- **Quantity model:** Ingredients have `quantity_type` of "precise", "imprecise", or "unmeasured". Scaling logic branches on this: precise scales mathematically, imprecise scales approximately, unmeasured stays unchanged.
- **Folk units:** an amount is imprecise from hedge words ("about", "~") *or* from a folk/body/vessel unit ("3 soup spoons", "a pinch", "a good splash"). `app/services/folk_units.py` splits those into **countable** (count is real → "3 soup spoons" doubles to "6 soup spoons", pluralized) and **non-linear** (a geometry, not a quantity → "3 fingers of water" stays verbatim and the cook gets the multiplier via `scale_note`). `frontend/src/utils/quantity.js` mirrors the same vocabulary at entry time — **keep the two lists in sync.**
- **Handoff delivers:** `POST /recipes/{id}/handoff` takes an **optional** recipient. With neither `to_email` nor `to_user_id` it is link-only: it mints a token the sender shares via `navigator.share` (copy-link fallback) from `HandoffInvite`'s share stage. Link-only handoffs are deliberately *not* deduped — each is an independent grant.
- **The invite token is the capability:** `/recipes/invite/{token}` returns the **whole** recipe unauthenticated. This is not a soft wall (it used to be, and that inverted the product). Only the owner's private `notes` and account ids are withheld. Don't reintroduce body gating.
- **Soft delete:** Recipes use `deleted_at` timestamp. All queries must filter `WHERE deleted_at IS NULL`.
- **Single transaction pattern:** Recipe creation flushes mid-transaction to get auto-generated IDs for child rows before final commit.
- **Visibility: a concrete per-item value + a profile that picks the default.** Since #68. A **recipe or post** carries its own `visibility`, one of three literal values — `public` (anyone; eligible for Browse), `friends` (the owner's accepted friends only), `private` (only the owner, + accepted handoff grantees for recipes). New items default to `friends` (schema level); `Post`'s DB `server_default` is `"friends"` and `Recipe`'s stays `"private"` as a bypass safety net. The value is **stored literally**, never a pointer to the profile — a label like "Friends only" means friends only, permanently. The create-time `VisibilityChoice` / edit-time `VisibilityControl` are 3-way ("Everyone" / "Friends only" / "Only me") — there is **no "Follows your profile" option**. A **profile** (`User.profile_visibility`, `public | private`, **private by default**) is **not consulted at read time**: it only (a) picks the default the create form auto-selects for a new item — except mid-post (#81), where a recipe written from the meal composer starts from the POST's visibility instead, still stored literally — ("Everyone" on a public profile, "Friends only" on a private one) and (b) drives the bulk sweep — so flipping the profile changes **nothing** already stored. The sweep is `PATCH /auth/me` with `apply_visibility_to_all` (`public | friends | private`): it sets every one of the caller's recipes and posts to that concrete value, offered by the Profile-page confirm dialog both ways ("make everything public" / "make everything friends-only"). `can_view` (recipes) and `can_view_post` (posts) are the two read rules, sharing one truth table; `get_recipe`/`browse` gate on `effective_visibility()`, which returns the recipe's own concrete `visibility` (Browse shows `public` only). The handoff grant is **orthogonal** (a grantee reads their one recipe regardless of visibility/friendship).
- **Blocking (#85): a block outranks visibility, but not a grant already given.** The check lives inside `_resource_is_visible` **before** the `public` short-circuit, so it covers every recipe and post read through `can_view`/`can_view_post` at once. Three properties are deliberate and each looks like a bug from one angle: (1) the effect is **symmetric** from a **directional** row — one block hides the pair from each other everywhere; (2) it **deletes** the friendship rather than suspending it, so unblocking does not restore it; (3) an **already-accepted handoff grant survives** — you genuinely handed them that dish, and a block means "no new contact", not "unsend". A *new* grant cannot cross a block (`handoff_recipe` 404s), or the grant branch would be an uncapped channel into a blocker's kitchen. The cut is at OFFER time, not accept time (#88): a link-only token or emailed invite minted BEFORE the block stays claimable/acceptable, because the token is the capability and the cook chose to send it — `claim_invite` and `accept_handoff` deliberately carry no block check. Every denial is a **404**, byte-identical to what an unknown user gets — a blocked person must never be able to detect the block. And blocking must not **destroy** anything the caller can't get back: the Kept shelf's prune is permanent, so a block hides a bookmarked recipe without deleting the save row, and unblocking restores it. See TESTING.md invariant 9.
- **Read is not write.** `can_view` answers *read* only. Editing and deleting are owner-only, enforced separately by a `user_id` filter in `patch_recipe`/`delete_recipe`; `handoff_recipe` requires ownership too. A grantee can read and cook, never change someone else's record of the dish. Don't collapse these two questions into one rule.
- **Auth input validation:** `UserCreate` (`app/schemas/user.py`) strips whitespace on names then requires ≥1 char (so `""` and `"   "` fail by the same rule), max 80; password 8–72 bytes (72 is bcrypt's own ceiling — longer is silently truncated). The rules are on the **input** model only, deliberately: tightening `UserResponse` would turn an already-stored blank name into a 500 on read.
- **One place for error copy:** `toUserMessage` in `frontend/src/api/client.js`. A FastAPI 422 arrives as an array of objects; rendering it raw once put `[object Object]` in front of a user who had just chosen a short password. It surfaces every failing field (deduped), passes a router's deliberate `detail` string through untouched, and separates "no response at all" (offline) from "the server said no". Route new error UI through it rather than formatting inline.
- **Step check-off is session-only.** `doneSteps` in `RecipeBody` is component state, deliberately not persisted — a half-cooked recipe isn't a document state worth storing, and stale check marks on a later cook would be worse than none.

## Frontend

Located in `frontend/`. React + Vite + Tailwind CSS + React Router + Axios. See `ARCHITECTURE.md` for the full component/page map.

**Design system — the "kitchen" / sticker look** ("Kamala's Recipes"–inspired: bold ink outlines, hard solid offset shadows, saturated color-block fields, chunky display type). The palette source of truth is `frontend/tailwind.config.js`; shared class utilities live in `src/index.css`.
- **Palette:** cream `#FBF3E2` (app bg) · card `#FCF8EE` · ink `#2E3A24` (outlines + primary text) · ink-soft (secondary text) · line (hairlines) · terra `#B5502A` (the action accent — buttons/links/active) · peach (hero/story color blocks) · coral (accent bars) · saffron (badges/step-note accents) · sage `#A8C69A` (affirmative: saved/sent/done) · brick `#C0442F` (emphasis/destructive) · plum `#8A3D5A`.
- **Color roles:** `terra` = interactive intent (buttons, links, active nav); `plum` = **the person's name only** (bylines: "from Lola"); `saffron` = the person's-knowledge accents (the story card, the per-step note callout); peach/sage = playful colour blocks + sticker badges. **`periwinkle`, `mint`, `coral`, `paper`, `herb`, `growth`, `soil` were DELETED** — Tailwind emits nothing for an unknown colour, so referencing one renders as no fill at all, silently (it has shipped three times). `frontend/src/palette-usage.test.js` now fails on any reference to a colour the config doesn't define..
- **The sticker system:** `.sticker` / `.sticker-press` = ink outline + hard `0_4px_0` offset shadow. Plus `.field`, `.btn-primary`, `.chip`, `.error-pill`, `.section-label`, `.story-callout` — compose these rather than re-deriving.
- **Type:** TWO families loaded — Fraunces (`font-display`) for headings, titles and most UI, and Nunito Sans (`font-sans`) for body. Those are the only two in `index.html`. `font-hand` does not exist. (`font-serif`/Cormorant Garamond **does** still exist as a config key, but it is legacy and deliberately not loaded — don't use it. `tailwind.config.test.js` excludes it from the must-be-loaded invariant and comments it as legacy.)
- **No handwritten face.** Caveat, Shantell Sans, Patrick Hand, Architects Daughter and Kalam were each tried for a person's story and their per-step notes, and all five were cut: it's body content someone cooks from, the data is typed text (so a script face implies a recording that doesn't exist), and it reads as a consumer novelty against the discipline of the rest of this design. A person's presence is signalled STRUCTURALLY instead — the saffron card, the quote stamp, the attributed heading, Fraunces italic. See the long note in `frontend/tailwind.config.js`; `tailwind.config.test.js` asserts no `hand` family exists **and** that every family the app references is actually loaded (a referenced-but-unloaded font falls back to a system face and fails silently).
- **Logo:** the `issei.` wordmark — a `Wordmark.jsx` component rendering cream Fraunces on an ink sticker plate (the one inverted element in the app). A `bare` prop drops the plate for use on an already-colored field (e.g. the photo-less `CoverImage` placeholder). `MarkerTitle` gives section headers a highlighter-swipe.
- **The three verbs — keep them distinct.** One verb per act, because "keep" used to mean two things and testers read the authoring card as "make my own copy of this", which is the removed Remix model reached by wording alone:
  - **Share a meal** — post a photo + dish name (a post is not a recipe).
  - **Write a recipe** — author your own. `/add` → `PlantRecipe`; the form's heading is "Write a recipe" and its submit is "Save this recipe". Also reachable **mid-post** from the meal composer's "Write one" (#81): the composer hands its draft over in router state, the recipe saves for real, and you land back on the post with it attached (the draft is all strings + an already-uploaded Cloudinary URL, so the round trip is lossless). The recipe starts from the post's dish name, description and photo (name, description, cover — the "zero re-entry" the social-feed design specifies) and from the post's visibility — both changeable, both stored literally.
  - **Keep** — put SOMEONE ELSE'S recipe in your kitchen (#57): a bookmark, never a copy. "Keep this recipe" / "Kept ✓" on `RecipePage`, the Kitchen's **Kept** tab, and the invite page's "Keep this recipe →" (which claims a handoff grant — same meaning).
  - **Ask** — request the recipe behind SOMEONE ELSE'S meal (#79). "Ask for the recipe" / "Asked ✓" on the post card and the post page; the cook answers on `/requests`, and answering mints a handoff grant, never a copy. A fourth first-class act, not a reaction: never call it a like, a want, a save or a follow, and never render its count to anyone but the cook (POSITIONING's fourth invariant) — the cook sees it on their OWN card and post page, hidden at zero, because "0 people asked for this" under your own dinner is the discouraging line the private count exists to avoid.
  Never use "keep" for authoring, and never use "save"/"copy"/"version"/"remix"/"make it yours" for keeping.

**Conventions:**
- JWT in localStorage under `issei_token`; user object under `issei_user` — but go through **`lib/currentUser.js`**, not `localStorage` directly, for anything a person LOOKS at (name, email, avatar). It owns the cache: `patchUser` merges over a fresh read (a `{...user}` spread from a stale closure was reverting a just-uploaded photo), `useCurrentUser()` re-renders subscribers, and `reconcile()` syncs `GET /auth/me` once per app start (nothing used to, so a photo added on one screen stayed invisible on another). Reading `id` or `profile_visibility` straight from localStorage is still fine — an id can't drift.
- All API calls go through `src/api/client.js` (axios instance w/ base URL + auth header + 401 handling + `toUserMessage`); recipe/sharing calls in `src/api/sharing.js` (was `api/lineage.js`).
- Components in `src/components/`, pages in `src/pages/`; hooks only, no class components.
- No UI libraries (no shadcn, no MUI) — custom Tailwind only.
- **Env:** `VITE_API_URL` (backend base URL), `VITE_APP_VERSION` (optional; stamped onto feedback so a report says which deploy it came from). `VITE_FEEDBACK_URL` is GONE — feedback is a native form at `/feedback` writing to the `feedback` table, not an external link. See `frontend/.env.example`.
- **The add-recipe form opens with TWO blank ingredients and TWO blank steps** (`STARTING_INGREDIENTS` / `STARTING_STEPS` in `RecipeForm.jsx`). It used to be three of each, deliberately: a tester once typed their whole method into step 1 and every ingredient into ingredient 1, because a single empty box gave no hint they were separate entries. The owner cut it (3 → 1 → 2 on 2026-09-08) because the form read as a chore on open. TWO is the smallest count that still shows the SHAPE — this is a list, not a box — and the "one step per box" copy backs it up. Both the count and that line are pinned by a test; keep both.
