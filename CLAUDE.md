## What This Is

A deployed full-stack app (FastAPI backend + React frontend) for **sending one recipe from the person who cooks it to the person who just tasted it and asked for it** — *issei* (一世) = "first generation." Someone cooked you something you'd never had before; this is how they send it to you. A recipe is attributed to a *person* (the dish is the title, the person is the byline "from Lola"); imprecise measurements like "a dash" or "3 soup spoons" are preserved verbatim as fidelity, never normalized; per-step notes carry the knowledge an ingredient list can't hold; and the recipient reads the whole thing from a capability link with no account. The signature is **that handoff** — the fuzzy-quantity model is the supporting layer that makes what arrives honest. The UI is a warm, playful "kitchen" (bold sticker / color-block design). Backend on AWS ECS Fargate, frontend on Vercel, PostgreSQL (Neon) in production, SQLite locally.

> 3. **A recipient cannot edit.** `patch_recipe`/`delete_recipe` filter on `user_id`. Read is not write.

The garden UI and its docs were removed once the kitchen design was locked in; they remain in git history.

## Architecture

**App entry:** `app/main.py` — mounts seven routers (auth, recipes, upload, feedback, friends, posts, notifications) and a `/health` endpoint.

**Routers** (`app/routers/`) — endpoint definitions. Each router handles one domain: auth (signup/login/me — `login` now also returns `profile_visibility` and `photo_url` — plus `PATCH /auth/me` to edit name/email/password/profile_visibility/photo_url (all but email+password need no password — low-risk; `photo_url` is validated to a Cloudinary HTTPS host, or blank → NULL/monogram), `DELETE /auth/me` to delete the account, and the password-reset pair `POST /auth/forgot-password` / `POST /auth/reset-password`), recipes (CRUD + scaling), upload (Cloudinary photos — `POST /upload/recipe-photo` and `POST /upload/avatar`, the latter a square 400x400 face-gravity crop into `issei/avatars`), friends (the symmetric friend graph — social feed Phase 0). Recipes also has the sharing actions: `POST /{id}/cook`, `POST /{id}/handoff`, `GET /recipes/shared`, `POST /recipes/handoffs/{id}/accept`, the invite flow (`GET /recipes/invite/{token}` — unauthenticated **full** recipe read; `POST /recipes/invite/{token}/claim`; `GET /recipes/invite/{token}/preview` — crawler-facing OpenGraph HTML so a shared link unfurls as the recipe, see `services/invite_og.py`), plus the KEEP surface (#57): `POST /recipes/{id}/save` / `DELETE /recipes/{id}/save` (bookmark a recipe you can already read — gated on `can_view`, so keeping never widens access — and drop your own bookmark; a NEW keep notifies the cook anonymously, deduped while unread so a keep/unkeep loop can't flood their inbox, and `RecipeResponse.keeper_count` carries the tally to the OWNER only, #96) and `GET /recipes/kept` (the shelf: recipes handed to you MERGED with ones you kept, each re-checked through `can_view`, plus an `unreachable_count` for ones the cook has since restricted or deleted). Note `can_view` must NEVER consult saves — a save row is reader-created, so trusting it would be a self-grant; `services/sharing.py` does not import `RecipeSave`. Recipes also has the **optionally-authenticated** `GET /recipes/browse` (anonymous is fine — it's the app's one unauthenticated JSON feed — but a signed-in viewer is resolved via `get_current_user_optional` so their blocks are honoured; it was the one public surface a block couldn't otherwise reach), `GET /recipes/export` (#105 — every recipe the CALLER WROTE as JSON, own-recipes-only and `deleted_at IS NULL`; declared before `/{id}` so the literal path isn't read as an id. Deliberately not the Kept shelf and deliberately not a PDF — see Key Design Decisions), and `GET /recipes/ingredient-suggestions` / `GET /recipes/field-suggestions` (the caller's own past ingredients / sources+cuisines for form autosuggest, self-scoped). Friends has `POST /friends/request`, `POST /friends/{id}/accept` (addressee-only), `DELETE /friends/{id}`, `GET /friends` (accepted friends; optional `?order=active` sorts by each friend's most-recent *visible* post — the Feed presence strip #75 — vs the default `recent` = friendship recency for the Friends page), `GET /friends/requests`, `GET /friends/suggestions` (seeded from the handoff graph), `GET /friends/discover` (the app-wide directory + `?q=` name search — everyone except you, your ACCEPTED friends and anyone in a block relationship with you. Someone the caller has ASKED deliberately STAYS listed, carrying `friend_state` (`none` | `requested`) so the row reads "Requested" instead of the person silently vanishing — which a real user read as "did that work, or did I just remove them?". An INCOMING request is hidden instead, because it already has a home in `GET /friends/requests` (rendered above this section on the Friends page) and listing it here too showed one request twice with two live Accept buttons. No `friendship_id` is returned at all — no directory row has an action that needs one. The 50-row cap applies ONLY to addable strangers; anyone you asked is returned outside it, so the cap can never drop the person the label exists to keep; #80's fix for "I can't find how to add people". Discloses name+photo to any signed-in user, which `/u/{id}` already did — what's new is that it's ENUMERABLE. Deliberately NOT gated on `profile_visibility` (never consulted at read time, and private by default → an empty list); email is not searchable. Declared before `/profile/{id}` so the literal path isn't read as a user id), `GET /friends/profile/{id}` (read-only profile — returns the target's `profile_visibility`, `photo_url`, recipe and post counts the caller may see (gated by the visibility model), and `friend_count` (a symmetric public number, NOT caller-gated)), the REPORT surface (#87): `POST /friends/reports` (report a person — `reason` from a five-name vocabulary plus the reporter's own optional words. Three deliberate properties: it is **NOT gated on blocking in either direction**, unlike the five routes in this file that do, because otherwise a harasser who blocks their victim becomes permanently unreportable — the block turning into cover for the person who earned it; the reported person is **never told**, since telling them turns a safety mechanism into an escalation trigger; and only ONE report per reporter stays open at a time, deduped in Python because the rule has a state predicate in it — a second report with new words APPENDS to that row rather than being discarded, which the first version got wrong: with no way to close a report, a genuinely new incident weeks later was thrown away while the UI said "we'll take a look" about it. 204 either way, so a duplicate is indistinguishable from a first. **No read endpoint** — that needs an admin role this app has no concept of, and inventing one to avoid opening a database console would be the larger mistake), and the BLOCK surface (#85): `POST /friends/blocks` (block someone — mutual invisibility from then on; also deletes the friendship, drops pending asks both ways, and clears notifications between the two, all in one transaction), `GET /friends/blocks` (only who YOU blocked — never who blocked you, which would turn a protection into a notification, and the only route back since a blocked profile 404s) and `DELETE /friends/blocks/{user_id}` (removes just your own row; does NOT restore the friendship). The friends list / requests / suggestions also carry each person's `photo_url`. Posts (the presence feed — social feed Phase 1a) has `POST /posts` (share a meal: photo + dish name, optional description, optional link to a recipe you own), `GET /posts/feed` (newest first, keyset-paginated via `?before_id=`; no like button; `?scope=friends|everyone` — `friends` (default) = accepted friends' posts + your own, `everyone` = **public** posts from people you're NOT friends with, scoped in SQL to `visibility == "public"` so a stranger's friends/private post can't leak. **The user-facing toggle is GONE (#94, un-shipping #70)** — `everyone` survives as the COLD-START source only: the client asks for `friends`, and if nobody but the caller has posted it fetches `everyone` and renders it under "While you find your people". Home is otherwise the people you know), `GET /posts/browse` (built for Browse's Meals tab, which #94 un-shipped, so **nothing calls it today** — every `visibility == "public"` post, newest first, uncapped so the client can search the full set; the post counterpart of `GET /recipes/browse`, and unlike the everyone-feed it includes own+friends' public posts), `GET /posts/{id}` (author, a friend of the author, **or anyone on a public post** — which is what lets someone who isn't a friend open a public meal from a shared link; else 404), `PATCH /posts/{id}` (edit your own meal — FOUR fields since #106: dish name, description, visibility and the photo (host-checked through `services/media.py`; it cannot be CLEARED, since `Post.photo_url` is `nullable=False`). Author-only, 404 for anyone else. Partial, so `null` = unchanged and `""` clears a description. THREE deliberate omissions, each one a rule that would otherwise live only in the client (the photo was a fourth until #106): not the **author** (a post is "I made this"); not the **attached recipe** (attaching one to a post people asked about is *answering* them, which is `POST /{id}/fulfill`'s job, grants and notifications included — doing it quietly here would attach the recipe and leave every ask pending underneath it); and not the #97 **read-mark** — `is_new` keys on the post id, which an edit doesn't move — so an edit never resurfaces as unread, and it notifies nobody), `DELETE /posts/{id}` (author-only), `GET /posts/users/{id}` (a user's posts for their profile grid, friend-or-own gated). The feed/single/profile responses null a post's `recipe_id` when the viewer can't read that linked recipe (private or soft-deleted), so a "See the recipe" link never dead-ends, and carry the post author's `author_photo_url` for the avatar. Recipes also has `GET /recipes/users/{id}` — a user's recipes for their profile grid, `can_view`-gated (own → all; friend → `public` + `friends`; non-friend → `public` only), the recipe counterpart of `GET /posts/users/{id}` (both power the tabbed `ProfileContent`). Posts also carries the request loop (#79): `POST /posts/{id}/request` (ask the cook — open to **anyone who can `can_view_post` the post**, deliberately not friends-only, and only where the caller can't already read a recipe for it; a fulfilled row is re-opened rather than silently blocking a re-ask, and the cook's notification is deduped while unread so an ask/retract loop can't flood the inbox), `DELETE /posts/{id}/request` (**the one post route with no read check** — ask on a public meal, watch the cook make it friends-only, and a `can_view_post` gate here would make your own ask permanent: 404 on the post AND 404 on withdrawing it, with your name still on their `/requests` forever. A row you created is yours to delete; that isn't a read of someone else's content. It does require a **pending row or** read access, though, or polling it would read a private post's dish name, photo and author out of the response body — and when the pending row is the ONLY credential it answers **204 with no body**, since `PATCH /posts/{id}` lets a cook rename the dish and rewrite the description in the same call that hides it, so a 200 body would be content that was never on the asker's screen; both clients read exactly one field (`requested_by_me`) off this response, and an absent body already means false), `GET /posts/requests/incoming` (the cook's asks + who asked — the only place a requester's NAME is returned; the COUNT also reaches the author on their own posts via `request_count`, which stays `None` for every other viewer), and `POST /posts/{id}/fulfill` (author-only, own-recipe-only; mints an accepted `Handoff` per pending requester, so a **private** recipe is delivered without its visibility changing — and since #99 this is ALSO the attach-after-publishing path, because `post.recipe_id` is set outside that loop, so with nobody waiting it simply attaches and notifies no one), `DELETE /posts/{id}/recipe` (#99 — unlink, author-only, idempotent; answers nobody, revokes no grant, re-opens no fulfilled ask). Posts also carries the feed read-mark (#97): `POST /posts/feed/seen` advances `User.last_feed_seen_post_id` to the newest post the caller has seen, and `GET /posts/feed` returns `is_new` per post so the client can draw a "You're all caught up" divider. **`is_new` is a FLAG, never a FILTER** — the feed returns exactly the same posts either way, and nothing expires: a post is the top of the funnel to a handoff, so a vanishing post would take the ask with it. The mark is an **id, not a timestamp** (`created_at` is second-granular on SQLite, so a same-second post would be wrongly counted read — the same reason feed pagination is keyset on `id`), it moves **forward only**, and it is NOT a foreign key (a FK would `SET NULL` when that post is deleted, resetting the user to "never looked"). Your own post is never `is_new` to you, and `is_new` is `None` off the feed — Browse, a permalink and a profile grid have no concept of new. It is also the prerequisite for #89: "3 friends posted since you last looked" is the whole content of a push prompt and could not be computed before this. Notifications has `GET /notifications` (the caller's inbox, keyset on id, returning `unread_count` with the rows) and `POST /notifications/read`, plus the PUSH surface (#89): `GET /notifications/vapid-key` (unauthenticated — the server's public key, which a browser needs to subscribe; reports `configured: false` rather than 404ing so a client never subscribes against an empty string), `POST`/`DELETE /notifications/subscribe` (per-DEVICE rows in `push_subscriptions`, idempotent on the browser-minted `endpoint`; a shared device moves to whoever granted last, because silently delivering one person's notifications to another is the worse failure) `POST /notifications/run-daily-prompt` (the scheduler's entry point — no user, authenticated by a shared secret via `compare_digest`, and **disabled rather than open when the secret is unset**; 404 for a wrong key and an unset one alike. Triggered hourly by `.github/workflows/daily-prompt.yml`. An endpoint rather than a scheduled ECS task because the deploy pipeline never runs `cdk` and the CDK task-def family collides with the one the pipeline re-renders — a `cdk deploy` for a cron rule would replace the running prod image from the operator's local tree. Actions cron drifts and drops runs, which is why `is_due` asks "has their hour PASSED today and have they not been sent" rather than "is it exactly their hour": a late run still catches everyone, and `prompt_sends`' UNIQUE (user, local_date) is what makes catch-up safe), and `POST /notifications/subscribe/rotate` (**the app's only deliberately unauthenticated write** — `pushsubscriptionchange` fires inside a service worker with no page, no localStorage and no JWT, so the OLD ENDPOINT is the credential, exactly as an invite token is; the `user_id` comes from the row being replaced, never the request). `main.py` also serves `GET /health` and `GET /health/ready`. **67 routes total** — this number has changed several times; re-count with `grep -rn "^@router\.\|^@app\." app/` rather than trusting it.

**Models** (`app/models/`) — **eighteen** SQLAlchemy ORM models: `user` (carries `profile_visibility` — `public | private`, default private — which picks the create-form default and drives the bulk sweep, but does **not** gate reads; and `photo_url` — a nullable Cloudinary URL for the profile picture, NULL → the first-letter monogram; not gated by `profile_visibility`; and the two #105 settings — `invite_permission` (`anyone | friends`, default the PERMISSIVE `anyone` so nothing changed for an existing account; gates who may pre-address a handoff to you, which is the one contact channel blocking cannot reach) and `default_recipe_visibility` (three values, backfilled from `profile_visibility` so no create form moved on the day it shipped; picks what the form STARTS on and nothing more); and `last_feed_seen_post_id` — the feed read-mark, #97: an ID not a timestamp (second-granular `created_at` misses a same-second post) and NOT a foreign key (a FK would `SET NULL` on post deletion and reset the user to "never looked")), `recipe`, `ingredient`, `ingredient_section`, `step`, `cook_event`, `handoff`, `feedback`, `password_reset`, `friendship` (symmetric friend graph, one row per unordered pair — social feed Phase 0), `post` (a shared meal for the presence feed — photo + dish name, optional description, optional link to a recipe the author owns, its own concrete 3-value `visibility` with `server_default "friends"`; no ingredients/steps — social feed Phase 1a), `recipe_request` (#79 — an ask on a post; unique on (post, requester), `state` pending|fulfilled), `notification` (the inbox — recipient + actor + nullable post/recipe refs that `SET NULL` so a notification outlives its subject, `read_at`), `recipe_save` (#57 — a BOOKMARK: this user keeps this recipe. **Schemas** (`app/schemas/`) — Pydantic models for request/response validation. Separate from ORM models to control what's exposed at the API boundary.

**Services** (`app/services/`) — business logic decoupled from HTTP layer. Fourteen: `scaling.py` handles the three-type quantity model (precise/imprecise/unmeasured), `folk_units.py` holds the folk-unit vocabulary, `quantity.py` classifies a written amount into that model (shared vocabulary with `folk_units`), `recipe_ai.py` is the OpenRouter call behind `POST /recipes/parse` (strict-schema extraction, amounts preserved verbatim, falls back to a local parser when unavailable), `growth.py` computes `soul_count`/`growth_stage`/`growth_vitality` (still computed + returned on `RecipeResponse`, but no longer surfaced in the UI since the garden redesign), `sharing.py` (formerly `lineage.py`) holds `can_view` (recipes) and `can_view_post` (posts) — the two single read-authorization rules — sharing one truth table (`_resource_is_visible`). In evaluation order: **a block between the two in EITHER direction → never visible, checked FIRST so it beats `public`** (a block that didn't outrank `public` would leave every public recipe and post of theirs on your screen); then owner OR `public` OR (`friends` AND the viewer is an accepted friend via `are_friends`) OR — recipes only, orthogonally — an accepted handoff grant, **which a block deliberately does NOT override** (you gave them that dish; a block stops new contact, not what's already handed over — though a NEW grant can't cross a block, `handoff_recipe` refuses). Both take optional precomputed `is_friend`/`blocked` so a list endpoint answers once per page instead of once per row; plus `effective_visibility`, which returns the recipe's own concrete `visibility` unchanged (the profile is not consulted at read time; Browse shows recipes where `visibility == "public"`), `email.py` sends the password-reset email via AWS SES, `invite_og.py` builds the crawler-facing OpenGraph card for `GET /recipes/invite/{token}/preview` (so a shared invite link unfurls as the actual recipe), and `notifications.py` is the single producer of a notification (`notify()` — validates the type against a five-name vocabulary (`recipe_request`, `request_fulfilled`, `friend_request`, `friend_accept`, `recipe_kept`), never notifies you of your own act, dedupes against an identical unread row, and deliberately does NOT commit so it lands in the caller's transaction). **`recipe_kept` (#96) is ANONYMOUS at the API boundary**: the row stores `actor_id` because `notify()` needs it, but `routers/notifications.py` nulls every actor field on the way out, so the line reads "Someone kept your Adobo" — the cook learns how many, never who. `push.py` is the one place a notification LEAVES the building (#89) — RFC 8292 VAPID plus RFC 8291 aes128gcm encryption, built on `cryptography` and `httpx`, both already pinned. **No new dependency**: the obvious choice, `pywebpush`, hard-depends on `requests`, and this codebase standardised on httpx. Hand-rolled crypto fails SILENTLY, so `tests/test_push.py` DECRYPTS what it produces from the receiver's side — that round trip caught a real bug (the content key was derived from a zero salt while the header carried the random one, a body no browser could ever have read). It DEGRADES rather than raising: with no key configured every send is a logged no-op, so a deploy without the secret behaves exactly as before push existed — the opposite of `email.py`, which raises and leans on its one HTTP caller, a pattern that would make a scheduled job fail silently. Only **404 and 410** mean a dead subscription; pruning on any 4xx would empty the table on the first botched key rotation, and a subscription can only be recreated by the user re-granting on that device. `prompt.py` answers who is due and what the nudge says (#89) — and the count is the careful part: the obvious `COUNT(*) WHERE user_id IN (friends) AND id > mark` mirrors the feed's SQL, which is the trap, because the feed's correctness lives in the Python `can_view_post` filter two lines later. That aggregate counts a friend's PRIVATE post and a BLOCKED person's post. It also counts DISTINCT authors, not posts, since the copy says "3 friends posted". Zero sends NOTHING, like every other absence in this app. `blocks.py` holds `is_blocked` (either direction; False for a None id or for one person against themselves) and `blocked_ids` (the bulk set for list endpoints) — the third single-predicate service, `media.py` holds `is_our_image_url` / `require_our_image_url` (#106) — the single rule for whether a client-supplied image URL is one of ours (HTTPS + a host ending `.cloudinary.com`), called by ALL FIVE writes that accept an image URL — `PATCH /auth/me`, `POST /posts`, `PATCH /posts/{id}`, `POST /recipes` and `PATCH /recipes/{id}` (the recipe pair via `_check_recipe_image_urls`, cover + every step photo, before any DB write). It is a service because the inline copy in the first router never reached the second, which is how #98 shipped an unvalidated photo field, and `friends.py` holds `are_friends` — the single friendship predicate (like `can_view`), for the symmetric friend graph.

**Auth** (`app/auth.py`) — JWT-based stateless auth. `get_current_user` is the dependency injected into protected endpoints. `get_current_user_optional` (OAuth2 with `auto_error=False`) returns the signed-in user **or None** and never raises — a deliberately separate function rather than a flag, because one dependency that sometimes 401s and sometimes returns None is the ambiguity that leaks. It exists solely for `GET /recipes/browse`, which must stay readable without an account yet still honour a block.

**Migrations** (`alembic/`) — `alembic/env.py` imports all models and uses the app's engine directly. New models must be imported there for autogenerate to detect them.

## Key Design Decisions

- **Quantity model:** Ingredients have `quantity_type` of "precise", "imprecise", or "unmeasured". Scaling logic branches on this: precise scales mathematically, imprecise scales approximately, unmeasured stays unchanged.
- **Folk units:** an amount is imprecise from hedge words ("about", "~") *or* from a folk/body/vessel unit ("3 soup spoons", "a pinch", "a good splash"). `app/services/folk_units.py` splits those into **countable** (count is real → "3 soup spoons" doubles to "6 soup spoons", pluralized) and **non-linear** (a geometry, not a quantity → "3 fingers of water" stays verbatim and the cook gets the multiplier via `scale_note`). `frontend/src/utils/quantity.js` mirrors the same vocabulary at entry time — **keep the two lists in sync.**
- **Handoff delivers:** `POST /recipes/{id}/handoff` takes an **optional** recipient. With neither `to_email` nor `to_user_id` it is link-only: it mints a token the sender shares via `navigator.share` (copy-link fallback) from `HandoffInvite`'s share stage. Link-only handoffs are deliberately *not* deduped — each is an independent grant.
- **The message has TWO occasions, and the app asks rather than guessing (#102).** `defaultInviteMessage({ recipeName, asked })` returns either "You asked for my Adobo recipe — here it is 💛" (POSITIONING's own one-liner) or "Here's my Adobo recipe — I wanted you to have it 💛". The app genuinely cannot tell which: an **in-app request never reaches the share stage** — it is answered at `/requests` via `fulfillPost()`, which mints grants server-side without rendering `HandoffInvite` at all — so what arrives here is either an unprompted send or the founding case, someone who asked AT THE TABLE, which leaves no trace in any database. Defaulting to "you asked" would be false for the first; defaulting away from it throws away the truest line in the product. So two chips ("They asked for it" / "Just because"), defaulting to the unprompted one because that's what the app has evidence for — and tapping a chip **never overwrites words the sender typed** (`touched` guards it). The message box also gained a label and a line saying where the text goes; it always arrives pre-filled, so its placeholder was never seen and nothing told a sender the box was theirs.
- **The 💛 in that message is the SENDER's, and the app no longer signs its own copy with one.** It used to appear in exactly two shipping strings — the invite message and the You page's "More ways to share and connect are on the way. 💛" — so one glyph signed both the app's voice and a sentence meant to read like a person. The You-page line was removed (#102); it was also a roadmap promise on a settings screen, which is a thing to ship rather than to say.
- **`Handoff.note` is GONE (#102, migration `e7f8a9b0c1d2`).** The sender's message was persisted on every send and read by nothing — not `InvitePreview`, not `invite_og.py`, no frontend surface — so no recipient ever saw the stored copy and no screen ever displayed one. Two options were coherent (render it on the invite page so it survives a forwarded link and a truncated SMS, or stop keeping it) and the status quo was neither. The owner chose to drop it, so the message lives only in the sender's own texting app. `HandoffIn` no longer accepts it and `HandoffResponse` no longer returns it; **Pydantic ignores unknown fields by default**, so an older frontend build still sending one gets a 201 rather than a 422 — which matters because Vercel and ECS deploy independently. If it ever comes back, it comes back WITH a surface that shows it.
- **"no account needed" is on every unfurl card now (#102).** It used to live only in the `else` of the description branch, so the clause that answers a stranger's "why would I tap this?" appeared only on cards for recipes with **no** description — the emptiest ones. Nobody decided that; the two branches were written as alternatives for one `og:description` line. The cook's own words now follow the promise, and "on issei" was dropped from the sentence (`og:site_name` already says issei and the unfurl shows the domain), which buys back most of the room. Cost, stated honestly: iMessage shows roughly two lines, so a long description loses its tail.
- **What LEAVES the app is the message AND the link, on every path (#102).** `HandoffInvite.shareText()` is the one place that string is built (`body + '\n\n' + inviteUrl`), and both delivery paths use it: the share sheet, and the clipboard fallback for every browser without `navigator.share` (all desktop Firefox). The fallback used to copy the bare URL, so the sentence the whole compose stage exists to write never left the app for those senders — and the only confirmation appeared on a *different* button than the one they pressed. Three rules now: the confirmation lands on the button that was tapped; **a cancelled share sheet is not a failure** (it rejects with `AbortError`, and falling through to the clipboard flashed "Copied ✓" at someone who had just decided not to send, which reads as "it went"); and a real rejection (Safari's `NotAllowedError` outside a gesture) *does* fall through, because there the clipboard is the right answer. `HandoffInvite.test.jsx` stubs `navigator.share` and `navigator.clipboard` for all four cases — before #102 the delivery half had no test at all.
- **The Browse reassurance is three-way, because `friends` is not `private`.** `HandoffInvite` said "only someone with the link can open it" for both, and for a `friends` recipe that is false: `GET /recipes/users/{id}` is `can_view`-gated, so every accepted friend already opens it from your profile grid with no link. `friends` is the DEFAULT for a new recipe, so the wrong branch was the common one — and it contradicted `VisibilityControl` one tap earlier on the same recipe. `PlantRecipe` must pass `recipeVisibility={saved.visibility}`; without it the component falls back to its `'private'` default and tells someone who just published to Browse that their recipe isn't in Browse.
- **An invite recipient lands on the RECIPE, not the feed.** `Login.finishAuth` keeps `claimInvite`'s response and uses its `recipe_id`. It used to discard it and navigate to `/`, justified by a comment saying "Home leads with their recipe" — true of the hero-deck Home that #67 replaced with the friends feed, which shows a brand-new account nothing of their own at all. This is the highest-intent moment in the product: someone tapped "Keep this recipe →", signed up for that one dish, and was shown an empty feed. The `/welcome` exemption stays (a tutorial between them and the dish is the app talking over itself).
- **`client.js` has a `NO_REDIRECT_ON_401` set, not a single `/login` comparison.** A 401 clears the stale token everywhere, but must not REDIRECT on a route that is deliberately readable without a session — `/login`, `/invite/`, `/forgot-password`, `/reset-password`. One week-old `issei_token` in a recipient's browser was enough for `reconcile()` to 401 at app start and throw them off the invite recipe onto the sign-in screen, with the token already gone from the URL. Add future unauthenticated surfaces to that set rather than rediscovering this.
- **`/recipes/:id/handoff` is owner-only in the client too.** `GET /recipes/{id}` is `can_view`-gated so any reader loads it, but `handoff_recipe` filters on `user_id` — so a non-owner used to get the whole send screen ("This won't put **your** recipe in Browse", a compose box) whose only possible ending was a 404 pill after they'd written a message. `HandoffPage` now redirects a non-owner to the recipe. Read is not write, agreed with on both sides.
- **The invite token is the capability:** `/recipes/invite/{token}` returns the **whole** recipe unauthenticated. This is not a soft wall (it used to be, and that inverted the product). Only the owner's private `notes` and account ids are withheld. Don't reintroduce body gating.
- **Soft delete:** Recipes use `deleted_at` timestamp. All queries must filter `WHERE deleted_at IS NULL`.
- **Single transaction pattern:** Recipe creation flushes mid-transaction to get auto-generated IDs for child rows before final commit.
- **Visibility: a concrete per-item value + a profile that picks the default.** Since #68. A **recipe or post** carries its own `visibility`, one of three literal values — `public` (anyone; eligible for Browse), `friends` (the owner's accepted friends only), `private` (only the owner, + accepted handoff grantees for recipes). New items default to `friends` (schema level); `Post`'s DB `server_default` is `"friends"` and `Recipe`'s stays `"private"` as a bypass safety net. The value is **stored literally**, never a pointer to the profile — a label like "Friends only" means friends only, permanently. The create-time `VisibilityChoice` / edit-time `VisibilityControl` are 3-way ("Everyone" / "Friends only" / "Only me") — there is **no "Follows your profile" option**. A **profile** (`User.profile_visibility`, `public | private`, **private by default**) is **not consulted at read time**: it only (a) picks the default the create form auto-selects for a new item — except mid-post (#81), where a recipe written from the meal composer starts from the POST's visibility instead, still stored literally — ("Everyone" on a public profile, "Friends only" on a private one) and (b) drives the bulk sweep — so flipping the profile changes **nothing** already stored. The sweep is `PATCH /auth/me` with `apply_visibility_to_all` (`public | friends | private`): it sets every one of the caller's recipes and posts to that concrete value, offered by the Profile-page confirm dialog both ways ("make everything public" / "make everything friends-only"). `can_view` (recipes) and `can_view_post` (posts) are the two read rules, sharing one truth table; `get_recipe`/`browse` gate on `effective_visibility()`, which returns the recipe's own concrete `visibility` (Browse shows `public` only). The handoff grant is **orthogonal** (a grantee reads their one recipe regardless of visibility/friendship).
- **Blocking (#85): a block outranks visibility, but not a grant already given.** The check lives inside `_resource_is_visible` **before** the `public` short-circuit, so it covers every recipe and post read through `can_view`/`can_view_post` at once. Three properties are deliberate and each looks like a bug from one angle: (1) the effect is **symmetric** from a **directional** row — one block hides the pair from each other everywhere; (2) it **deletes** the friendship rather than suspending it, so unblocking does not restore it; (3) an **already-accepted handoff grant survives** — you genuinely handed them that dish, and a block means "no new contact", not "unsend". A *new* grant cannot cross a block (`handoff_recipe` 404s), or the grant branch would be an uncapped channel into a blocker's kitchen. The cut is at OFFER time, not accept time (#88): a link-only token or emailed invite minted BEFORE the block stays claimable/acceptable, because the token is the capability and the cook chose to send it — `claim_invite` and `accept_handoff` deliberately carry no block check. Every denial is a **404**, byte-identical to what an unknown user gets — a blocked person must never be able to detect the block. And blocking must not **destroy** anything the caller can't get back: the Kept shelf's prune is permanent, so a block hides a bookmarked recipe without deleting the save row, and unblocking restores it. See TESTING.md invariant 9.
- **Field ceilings: generous, invisible, maxima only.** Since #100. Every recipe field was unbounded before — no `max_length` in the schema and no length on the column either (`Mapped[str] = mapped_column()` infers an unlimited VARCHAR) — so a single request could store a megabyte in a dish name. `app/schemas/recipe.py` holds the `Text40`..`Text4000` aliases and `MAX_INGREDIENTS`/`MAX_STEPS`/`MAX_SECTIONS` (100/100/30 — length caps alone don't stop a hundred thousand one-character ingredients). Values match what already existed rather than inventing a parallel scale: a dish name is **120** because a post's `dish_name` is 120 and #81 carries one straight into the other; `source` is **80** because it holds a person's name and `first_name` is 80; a story gets **4000**, the most of anything, because it carries the person. Three rules: (1) they exist to refuse abuse and protect the layout, **not to edit anyone** — no character counters in the UI, just an honest error at the wall via `toUserMessage`; (2) **maxima only** — nothing was made newly required, because `OriginIn.name` accepts `""` today and a test depends on it, and tightening a minimum is a different decision with a different blast radius; (3) `RecipeCreate` and `RecipeUpdate` carry **identical** ceilings — an edit accepting more would be a way in, and accepting less would make an already-saved recipe unsavable.
- **Read is not write.** `can_view` answers *read* only. Editing and deleting are owner-only, enforced separately by a `user_id` filter in `patch_recipe`/`delete_recipe`; `handoff_recipe` requires ownership too. A grantee can read and cook, never change someone else's record of the dish. Don't collapse these two questions into one rule.
- **Auth input validation:** `UserCreate` (`app/schemas/user.py`) strips whitespace on names then requires ≥1 char (so `""` and `"   "` fail by the same rule), max 80; password 8–72 bytes (72 is bcrypt's own ceiling — longer is silently truncated). The rules are on the **input** model only, deliberately: tightening `UserResponse` would turn an already-stored blank name into a 500 on read.
- **One place for error copy:** `toUserMessage` in `frontend/src/api/client.js`. A FastAPI 422 arrives as an array of objects; rendering it raw once put `[object Object]` in front of a user who had just chosen a short password. It surfaces every failing field (deduped), passes a router's deliberate `detail` string through untouched, and separates "no response at all" (offline) from "the server said no". Route new error UI through it rather than formatting inline.
- **A `<button>` centres its own content, and that is why a card is a flex column.** `RecipeCard`'s root button carries `flex flex-col`, which looks decorative and is not. A button vertically centres its content (a UA behaviour), and a grid item stretches to the tallest card in its row — so a card whose title took ONE line had its photo *and* its title pushed down by half the difference: 10px at 430px, measured in a real browser. An explicit flex column replaces that centring with top-down flow, so the photos and the FIRST LINE of every title stay level while each byline follows its own title. This was always true; a fixed two-line title slot (shipped, then removed for leaving a blank line under short names) had been masking it, which is why removing the slot appeared to *cause* the problem. `self-start` and `block` were both tried and neither works. No test in the suite can see this — jsdom has no layout engine — so `RecipeCard.test.jsx` asserts the two classes and explains why.
- **A feed is scanned; a permalink is read.** Long text is CLAMPED on a card and full on the page it opens. `PostCard` clamps the dish name to two lines and the description to three; `PostPage` clamps neither. Without that, a 500-character description (the #100 ceiling) shoved the next person's photo off the screen — the cost of one person writing at length was paid by everyone below them in the feed. The clamp is VISUAL only (the full text stays in the DOM, so it's selectable and searchable and nothing is truncated server-side), and the way to read the rest is to tap the text itself, which shares the photo's `onOpen` — deliberately not a "more" link, which would put a second control beside the card's one intentional action. Same clamp on a notification line, where a 120-character dish name sits at the tail of the sentence. If you ever clamp `PostPage`, the feed's truncation has nowhere left to resolve; a test pins that.
- **The person frames the photo; the server stopped deciding (#103).** Two lines of one feedback batch were the same defect — *"Hard to adjust the photo to center the subject"* and *"Can't edit profile photo to make sure it looks as u want"* — because the crop happened entirely server-side, after the upload, with no preview: Cloudinary's `crop: fill` centre-crops, so anything off-centre was cut and the person found out afterwards. `PhotoFramer.jsx` is a canvas the picked photo is dragged and zoomed inside, `usePhotoFramer.js` bridges it to the `frame` callback `photoUpload.upload()` now awaits, and every image the app takes goes through it (recipe cover, step photos, meal photo, avatar). Five things about it are load-bearing: (1) **no backend change** — the client sends an image ALREADY at the target ratio (`FRAME_RATIOS`: 4:3 cover, 1:1 avatar, matching the 800x600 / 400x400 the endpoints store), so `crop: fill` becomes a pure resize and `gravity: face` a no-op on a square, which also means an older client that doesn't frame behaves exactly as before; (2) it runs **after** the HEIC conversion, or an iPhone photo would never preview; (3) the result has **three** outcomes, not two — a `File` (use this), `undefined` (couldn't crop, upload the original) and `null` (cancelled, upload nothing) — and conflating the last two made a browser with no canvas encoder look like someone changing their mind; (4) **"Use this photo" is never disabled**, because with no preview the only other control is "Pick a different one", which strands someone whose photo is fine; (5) the clamp keeps the frame **always fully covered**, so no output can carry a transparent margin. Three defects the ship gates caught in the first version, each worth not repeating: the screen said **"Pinch or use the slider to zoom"** and implemented no multi-touch at all — and since the canvas carries `touch-none`, the browser's own pinch was suppressed too, so two fingers panned the photo on the app's primary input while a test pinned the false copy (`pointers` is now a Map of every live pointer, and `anchoredOffset` is exported and unit-tested because jsdom can't deliver a two-finger gesture); `setPointerCapture` was called **before** registering the pointer, so its exception took the whole gesture down with it (capture is an enhancement, the gesture must not depend on it); and the JPEG re-encode had **no background fill**, so a transparent PNG — an accepted upload that previously reached Cloudinary untouched and stayed a PNG — composited onto black. Output is filled with cream first. The second gate round added three more, all phone-facing: **three fingers becoming two is still a pinch** (the first version only handled 2→1, so lifting one of three left two fingers panning — the exact symptom the pinch work exists to remove); the draw effect now **redraws and re-clamps on resize/orientationchange**, because an offset legal at 400px wide is out of bounds at 300px and the clamp is the only thing guaranteeing full coverage — a rotation could otherwise put a cream band in the upload; and the sheet carries **`max-h-full overflow-y-auto`** like `RecipePicker`, since an avatar preview is square and on a 360px phone the frame plus controls can outgrow a short viewport with "Use this photo" off-screen. **No new dependency** — a canvas, pointer events and a wheel listener, against a frontend deliberately at five runtime packages. jsdom has no layout engine, image decoder or canvas encoder, so the tests pin the CONTRACT and the drag/zoom/pixel behaviour was measured in a real browser; the load effect's `cancelled` flag and its revoke-on-settle are fixes for a StrictMode double-invoke that revoked an object URL mid-decode and left "That image could not be opened" over a working preview.
- **A photo is editable wherever the thing that carries it is (#106).** Owner's call, reversing #98 for posts. Three separate gaps, all the same shape — the app let you ADD a photo and never CHANGE one:
  - **A post's photo** was excluded from `PATCH /posts/{id}` on the argument that "a different photo is a different meal, so re-shoot it as a new post". That describes what a post MEANS but answers the wrong question: the common case isn't a different meal, it's a photo that came out badly or the wrong one of two picked in a hurry, and the only remedy was delete-and-repost — which throws away the post's date, its place in every feed, and **any recipe asks already sitting on it**. `photo_url` is back on `PostUpdate`, and #98's *other* objection (it had no host validation) is answered rather than dropped.
  - **A recipe's cover and its step photos** were editable in the schema all along, and unreachable in the UI: `RecipeForm`'s filled state rendered an `<img>` with only a **remove ×**, so changing a photo meant deleting it and picking again — with the recipe briefly photo-less, and, if the new pick then failed, the old one already gone. **A real browser found this, not a test**: the edit form showed both photos and contained *zero* file inputs. Each filled state now carries a "Change photo" label beside the ×, as a SIBLING rather than a wrapper — a `<button>` inside a `<label>` is nested interactive content, and tapping × would also open the picker.
  - **`services/media.py` is the one host rule.** `require_our_image_url` — HTTPS, host must end in `.cloudinary.com`. It exists as a service because the inline copy in `PATCH /auth/me` did not reach the second caller: that's exactly how #98 shipped a photo field with no check. Its own tests caught TWO real holes, in two rounds. First a substring check for `".cloudinary.com/"` passed `https://evil.test/.cloudinary.com/a.jpg`, since the path is attacker-controlled — so the URL is parsed. Then the ship gate found the parsed version accepted `https://evil.test\@res.cloudinary.com/x.jpg`: **Python's `urlsplit` and the WHATWG parser browsers use disagree about where the authority ends when it contains a backslash**, so `urlsplit` reported `res.cloudinary.com` while a browser fetches from `evil.test`. A validator that trusts the wrong parser is worse than none. It now refuses any backslash before parsing, refuses userinfo, and requires the host to match `[a-z0-9.-]+` — three checks, because the failure mode is two parsers disagreeing rather than one being wrong. **All FIVE write surfaces that accept an image URL validate** — `PATCH /auth/me`, `POST`/`PATCH /posts/{id}`, `POST /recipes` and `PATCH /recipes/{id}` (the recipe pair via `_check_recipe_image_urls`, covering the cover and every step photo). The first pass guarded only the two PATCH routes and recorded the rest as deferred, which the ship gate correctly called out as 0 of 1 rather than 2 of 4: with the create routes open, the rule prevented nothing an attacker couldn't do through the front door. The count was wrong too — there were five surfaces, not four, and the fifth is the one #106's own new "Change photo" control writes through, so the feature that introduced the rule was writing past it. Also: a post's photo cannot be CLEARED (`Post.photo_url` is `nullable=False` — a post with no photo is not a post, so blank is a 422), while a recipe cover and an avatar can.
- **The three settings that shipped (#105), and why each has a consumer AND a test.** The two toggles removed the day before are the reason: one wrote a localStorage key nothing read, so tapping it changed nothing.
  - **"Only friends can send me recipes"** (`User.invite_permission`, `anyone | friends`) — the only SAFETY one, so it went first. `POST /recipes/{id}/handoff` takes a `to_email`, and a sender needs no relationship with you, nor even for your account to exist, to put a recipe, a byline, a story and their own name on your shelf. **Blocking cannot reach this** — there is nobody to block until after it has happened. Enforced for a recipient resolved by id OR by email, and resolving the email fixed a pre-existing hole: the block check fired on a resolved user, so an email-addressed handoff walked past #85 entirely. The email match is **case-insensitive** (otherwise the setting is one shift key away from doing nothing). Every refusal is the same **404 "User not found"** a block and an unknown user get, so it never says WHICH it was. It does **not** hide account existence: an address with no account gets a 201 and a pending invite, so the pair tells a sender that an address belongs to an account which restricts invites. That is accepted rather than papered over — signup already answers "Email already registered" and #80 lists every user by name, so a fake 201 would buy a signal the app gives away elsewhere at the price of telling a sender their recipe was delivered when it wasn't. **Link-only handoffs are never gated**: the token is the capability, and gating it would break the founding case. Default `anyone` — the PERMISSIVE value, deliberately: it is today's behaviour, and silently tightening every account would break sends already in flight.
  - **`GET /recipes/export`** — the caller's OWN recipes as JSON. Not the Kept shelf: a kept recipe is someone else's record held by a grant to READ, and exporting it would make "keep" mean the copy it has never meant. **JSON, not a PDF** — a keepsake artefact is the legacy-archive product POSITIONING keeps issei out of, and only a machine-readable file answers "what if this goes away?". `quantity_text` and `quantity_type` leave verbatim, which is the fidelity promise not stopping at the door. The client builds a Blob and an object URL rather than pointing an `<a href>` at the endpoint, because the request needs the Authorization header and a token in a query string ends up in history and logs.
  - **"New recipes start as"** (`User.default_recipe_visibility`, three values) — states directly what was INFERRED, and the inference lost a value: `profile_visibility` is two-valued while an item's visibility is three, so "friends" — the actual default for every new recipe — existed only as a private profile's side effect and appeared on no screen. **Not a fourth visibility value and not a live pointer**: per #68 an item's visibility is stored literally, so changing this moves nothing already saved (a test pins that). `profile_visibility` STAYS — it still drives the bulk sweep. The migration **backfills from `profile_visibility`** (public → `public`) rather than defaulting flat, so no existing account's create form changed behaviour on the day it shipped; the client's fallback chain ends in the old derivation for the same reason, since a cached user written by an older build has neither field. Both the recipe form and the post composer read it — one person has one sense of who they share with, and two defaults would be a settings screen asking a question nobody has.
  - **Units are still DEFERRED** as #63. Converting "3 fingers of water" is the shopping-list mistake; any unit setting has to touch precise amounts only and leave folk units verbatim.
- **Attaching a recipe to a post you already published IS answering (#99).** The gap: a recipe could reach a post only at CREATE time (the composer, or writing one mid-post per #81) or through `POST /{id}/fulfill`, which needs somebody to have asked. So a cook who posted the meal on Tuesday and wrote the recipe on Thursday had no way to connect them, and one who attached the wrong recipe could only delete the post. Three things about the fix:
  - **The backend already did it.** `fulfill_post` sets `post.recipe_id` OUTSIDE its pending-requester loop, so on a post nobody asked about the loop does nothing and the attach happens on its own. #99 was a missing SURFACE, not a missing mechanism — the only new route is the unlink. Worth knowing before adding an "attach quietly" endpoint: that was `PATCH /posts/{id}`'s dropped `recipe_id` (#98), and it left every pending ask still pending under an already-attached recipe.
  - **The copy warns BEFORE the tap.** Attaching mints a grant per pending requester and notifies them, which is right — but it is a bigger act than "link my recipe", so the button carries "This also sends it to the N people who asked" whenever N > 0 — on the "Change recipe" path as well as the first attach — and says nothing at zero (same discipline as the ask count itself: never render a zero on someone's own meal). It was first gated on "nothing attached", which assumed a linked recipe and a pending ask are mutually exclusive — they are not: `request_recipe` deliberately ALLOWS an ask when a recipe is linked but the asker can’t read it (a private recipe on a public meal; the response nulls `recipe_id` for them), so a public post collects asks with a recipe already attached and the author’s "Change recipe" tap answers them. Suppressing the sentence there hid the exact act it exists to disclose, which the ship gate caught. The controls live with the recipe LINK rather than in the edit form, because this is not a caption edit.
  - **`DELETE /posts/{id}/recipe` answers nobody and takes nothing back.** Grants already minted survive (you genuinely handed that dish over — a block doesn't unsend either, #85, and `can_view`'s grant branch carries their access, never the post's link); requests already `fulfilled` stay fulfilled; nobody is notified. It is idempotent — unlinking a post with no recipe is a 200, because the 404s there are about the POST, so a double-tap on a slow connection is harmless. The label is **"Unlink"**, never "Remove" or "Delete": a cook must not think this removes the recipe from their kitchen.
- **Step check-off is session-only.** `doneSteps` in `RecipeBody` is component state, deliberately not persisted — a half-cooked recipe isn't a document state worth storing, and stale check marks on a later cook would be worse than none.

## Frontend

Located in `frontend/`. React + Vite + Tailwind CSS + React Router + Axios. See `ARCHITECTURE.md` for the full component/page map.

**Design system — the "kitchen" / sticker look** ("Kamala's Recipes"–inspired: bold ink outlines, hard solid offset shadows, saturated color-block fields, chunky display type). The palette source of truth is `frontend/tailwind.config.js`; shared class utilities live in `src/index.css`.
- **Palette:** cream `#FBF3E2` (app bg) · card `#FCF8EE` · ink `#2E3A24` (outlines + primary text) · ink-soft (secondary text) · line (hairlines) · terra `#B5502A` (the action accent — buttons/links/active) · peach (hero/story color blocks) · saffron (badges/step-note accents) · sage `#A8C69A` (affirmative: saved/sent/done) · brick `#C0442F` (emphasis/destructive) · plum `#8A3D5A`.
- **Color roles:** `terra` = interactive intent (buttons, links, active nav); `plum` = **the person's name only** (bylines: "from Lola"); `saffron` = the person's-knowledge accents (the story card, the per-step note callout); peach/sage = playful colour blocks + sticker badges. **`periwinkle`, `mint`, `coral`, `paper`, `herb`, `growth`, `soil` were DELETED** — Tailwind emits nothing for an unknown colour, so referencing one renders as no fill at all, silently (it has shipped three times). `frontend/src/palette-usage.test.js` now fails on any reference to a colour the config doesn't define..
- **The sticker system:** `.sticker` / `.sticker-press` = ink outline + hard `0_4px_0` offset shadow. Plus `.field`, `.btn-primary`, `.chip`, `.error-pill`, `.section-label`, `.story-callout` — compose these rather than re-deriving.
- **Type:** TWO families loaded — Fraunces (`font-display`) for headings, titles and most UI, and Nunito Sans (`font-sans`) for body. A person's presence is signalled STRUCTURALLY instead — the saffron card, the quote stamp, the attributed heading, Fraunces italic. See the long note in `frontend/tailwind.config.js`; `tailwind.config.test.js` asserts no `hand` family exists **and** that every family the app references is actually loaded (a referenced-but-unloaded font falls back to a system face and fails silently).
- **Logo:** the `issei.` wordmark — a `Wordmark.jsx` component rendering cream Fraunces on an ink sticker plate (the one inverted element in the app). A `bare` prop drops the plate for use on an already-colored field (e.g. the photo-less `CoverImage` placeholder). `MarkerTitle` gives section headers a highlighter-swipe.
- **The three verbs — keep them distinct.** One verb per act, because "keep" used to mean two things and testers read the authoring card as "make my own copy of this", which is the removed Remix model reached by wording alone:
  - **Share a meal** — post a photo + dish name (a post is not a recipe).
  - **Write a recipe** — author your own. `/add` → `PlantRecipe`; the form's heading is "Write a recipe" and its submit is "Save this recipe". Also reachable **mid-post** from the meal composer's "Write one" (#81): the composer hands its draft over in router state, the recipe saves for real, and you land back on the post with it attached (the draft is all strings + an already-uploaded Cloudinary URL, so the round trip is lossless). The recipe starts from the post's dish name, description and photo (name, description, cover — the "zero re-entry" the social-feed design specifies) and from the post's visibility — both changeable, both stored literally.
  - **Keep** — put SOMEONE ELSE'S recipe in your kitchen (#57): a bookmark, never a copy. "Keep this recipe" / "Kept ✓" on `RecipePage`, the Kitchen's **Kept** tab, and the invite page's "Keep this recipe →" (which claims a handoff grant — same meaning).
  - **Ask** — request the recipe behind SOMEONE ELSE'S meal (#79). "Ask for the recipe" / "Asked ✓" on the post card and the post page; the cook answers on `/requests`, and answering mints a handoff grant, never a copy. A fourth first-class act, not a reaction: never call it a like, a want, a save or a follow, and never render its count to anyone but the cook (POSITIONING's fourth invariant) — the cook sees it on their OWN card and post page, hidden at zero, because "0 people asked for this" under your own dinner is the discouraging line the private count exists to avoid.
  Never use "keep" for authoring, and never use "save"/"copy"/"version"/"remix"/"make it yours" for keeping.
- **Language:** kitchen register — "Your kitchen", "Open your kitchen" (signup). Recipes are named by the **dish** ("Adobo"); the person shows as "from {source}" (from `origin_attribution`), the verb muted + the name emphasized in plum. The story card is headed "{Name}'s story" and a per-step note is headed "a note on this step" — **not** "In X's words" / "their words", which claimed a recording and verbatim speech that don't exist.

**The installable shell (#89).** issei is a PWA, and that is a *notification* decision rather than an
"apps are nice" one: **Safari on iOS grants Web Push only to a site added to the home screen**, so the
manifest is the precondition for notifications existing at all on the platform most of these people
are on. Five pieces, and the awkward parts of each are the point:
- `frontend/public/manifest.webmanifest` — `display: standalone`, cream `theme_color`, and three
  icons including a **maskable** one (Android crops any icon to its platform shape; a non-maskable
  wordmark loses its edges). All four PNGs were rendered from `public/favicon.svg` so the home-screen
  icon and the tab icon cannot drift.
- `frontend/index.html` — the manifest link, `theme-color`, and the **iOS-only** trio
  (`apple-touch-icon`, `apple-mobile-web-app-capable`, `-status-bar-style`). Not redundant with the
  manifest: Safari ignores the manifest's icons and its display mode, and without
  `apple-mobile-web-app-capable` an iOS install is a bookmark — and a bookmark gets no push.
- `frontend/public/sw.js` — **deliberately NOT a caching service worker.** Three handlers: `push` →
  `showNotification` (always, even for an unparseable payload — a push that shows nothing is a
  permission-revocation offence in Chrome), `notificationclick` → focus and navigate an existing
  window rather than opening a fourth copy, and `pushsubscriptionchange` → `POST
  /notifications/subscribe/rotate`. Adding offline caching here would be a second, riskier feature
  wearing the same hat; a test asserts there is no `fetch` handler and no `caches` use. It lives in
  `public/` because a worker's scope can't be broader than its own path, so the bundled
  `/assets/sw-abc123.js` could only ever control `/assets/`. Which also means **`define` never touches
  it**: the API base URL arrives in the registration's query string (`/sw.js?api=…`), because a worker
  can't read `import.meta.env` and — during `pushsubscriptionchange` — has no page to ask. The browser
  persists the script URL with the registration, so the value survives a cold start weeks later.
- `frontend/src/lib/push.js` — the one place that talks to `PushManager`. `pushAvailability()` returns
  **four** states, not a boolean, because each needs different copy: `ready`, `install-first` (iOS in a
  browser tab — *unavailable until installed*, which is not the same as unsupported and is the answer
  for most of the audience), `unsupported`, `insecure`. `enable()` fetches the server key BEFORE
  spending the person's one permission prompt, since subscribing against an empty key mints a
  subscription the browser calls a success and nothing can ever deliver to. `disable()` drops the
  SERVER row first — reversed, a row survives holding keys the browser threw away, and pruning it
  would need a 404/410 that never comes.
- `App.jsx` registers the worker on **every** load, signed in or not: rotation is handled inside the
  worker, so an unregistered device silently stops receiving anything with nothing to notice it by.
`Login.jsx` also sends `timezone` from `finishAuth` on every login and signup — the nudge fires at a
fixed hour in the RECIPIENT'S local time, so a user with no zone stored is never due for anything, and
nobody opens settings to volunteer a value the browser already knows.

**Conventions:**
- JWT in localStorage under `issei_token`; user object under `issei_user` — but go through **`lib/currentUser.js`**, not `localStorage` directly, for anything a person LOOKS at (name, email, avatar). It owns the cache: `patchUser` merges over a fresh read (a `{...user}` spread from a stale closure was reverting a just-uploaded photo), `useCurrentUser()` re-renders subscribers, and `reconcile()` syncs `GET /auth/me` once per app start (nothing used to, so a photo added on one screen stayed invisible on another). Reading `id` or `profile_visibility` straight from localStorage is still fine — an id can't drift.
- All API calls go through `src/api/client.js` (axios instance w/ base URL + auth header + 401 handling + `toUserMessage`); recipe/sharing calls in `src/api/sharing.js` (was `api/lineage.js`).
- Components in `src/components/`, pages in `src/pages/`; hooks only, no class components.
- No UI libraries (no shadcn, no MUI) — custom Tailwind only.
- **Env:** `VITE_API_URL` (backend base URL), `VITE_APP_VERSION` (optional; stamped onto feedback so a report says which deploy it came from). `VITE_FEEDBACK_URL` is GONE — feedback is a native form at `/feedback` writing to the `feedback` table, not an external link. See `frontend/.env.example`.
- **The add-recipe form opens with TWO blank ingredients and TWO blank steps** (`STARTING_INGREDIENTS` / `STARTING_STEPS` in `RecipeForm.jsx`). It used to be three of each, deliberately: a tester once typed their whole method into step 1 and every ingredient into ingredient 1, because a single empty box gave no hint they were separate entries. The owner cut it (3 → 1 → 2 on 2026-09-08) because the form read as a chore on open. TWO is the smallest count that still shows the SHAPE — this is a list, not a box — and the "one step per box" copy backs it up. Both the count and that line are pinned by a test; keep both.
- **Your own post card carries a ⋯; nobody else's does (#104).** Reported by a real user: *"I want to demote the post but don't know how to."* Everything they wanted already existed — the post page has Edit (dish name, description and VISIBILITY, which is the "demote") and Delete — but the card never said so, so those controls were reachable only by guessing that your own photo was tappable. `PostCard` now shows a ⋯ when `isMine && onOpen`, matching the ⋯ idiom on `/u/:id`: unlabelled is not the same as faint. **Both items NAVIGATE; neither acts on the card** — a Delete two taps from a scrolling feed is the mis-tap #92 and #98 both corrected — and they carry `state: { open: 'edit' | 'delete' }` so `PostPage` opens the matching control instead of dropping someone on a page to hunt through. `PostPage` gates that on ownership **as answered by the server** (`res.data.user_id`), not on the navigation, and clears the state with a `replace` so a back-then-forward can't reopen a confirm someone dismissed. It reads the ROUTER's `useLocation()`, not `window.location` — the latter has no `.state`, so the whole feature would compile, ship, and silently do nothing.
- **Feedback announces itself; the read path stays self-only (#101).** `GET /feedback` returns the caller's OWN notes and nothing else, and an `OWNER_USER_ID`-gated read-everything endpoint was rejected on purpose (it invents an admin role without the machinery a real one needs, fails open when the var is unset, and turns one 7-day bearer token in one phone's localStorage into read access over every tester's candid words). The problem was never the read rule — it was that reading meant remembering to open a database console, so a beta's worth of notes went unread. `POST /feedback` now emails the owner each new note via `services/email.send_feedback_notification`, **after** the commit and unable to fail the request (a "your feedback failed" message on feedback that saved fine would be the most self-defeating error in the app). The recipient is `FEEDBACK_NOTIFY_EMAIL`, defaulting to `SENDER_EMAIL` — **no new secret**, because SES needs the sender verified and, in the sandbox, the recipient too, so the one certainly-verified address is the one already configured. Both empty → logged no-op. To read what's already there: `DATABASE_URL=… python scripts/read_feedback.py` (SELECT-only, prints the host and never the credential; `--reports` is a separate flag because a report is a live case about two named people, not a note addressed to you).
- **The "Settings" section on the You page is GONE (owner's call, 2026-09-11)** — both toggles and the heading. "Open recipes at Ingredients & steps" wrote `cookingByDefault` and **nothing ever read it**, so it changed nothing (the same defect #102 removed one heading above). "Turn off animations" worked, but duplicated `prefers-reduced-motion`, which the OS already owns and which the app still honours in `prefersReducedMotion()` — someone who wants stillness sets it once for every app, and a per-browser copy doesn't follow them to another device. What's left on that page is all consequential: who can see your kitchen, notifications, blocked people, account. Don't add a display preference back without a consumer AND a test.
